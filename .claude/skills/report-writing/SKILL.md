# レポートの文章規約

参考: https://speakerdeck.com/nasuvitz/ai-kusai-bunshou-toha-nanina-no-ka

このレポートは人事担当者が読み、配置や後継者の判断に使う。
文章が印象的に見えることより、**何が起きているかが1回読んで分かること**を優先する。

## 書き終えたら必ず実行する

```bash
.venv/bin/relana demo --no-open
.venv/bin/python scripts/check_wording.py src/relana snapshots
```

指摘が0件になるまで直す。**注意書きを読むだけでは守られないので、機械的に点検する。**

機械的な点検は語句しか見ない。**生成した HTML を自分で読み返す工程を必ず入れる。**
次の「出力を読み返すときの点検」に沿って、1ページずつ見る。

## 原則

### 0. 「どれが」「誰が」を特定して書く

集合について書くとき、**その集合の中身を出す**。
件数だけの文は、読んだ人が次に何をすればいいか分からない。

| ❌ | ⭕ |
|---|---|
| この人を除くと、会議でつながる集団が2つ以上に分かれる | この人を除くと、管理本部 5名（中村098・加藤100・小林099・山本097・渡辺096）が残り78名とつながらなくなる |
| 3名が孤立します | 山崎081・小川030・山下027 が誰とも会議でつながらなくなります |
| 1件（u_089…） | 1件（石井089） |
| 部門をまたぐ接点が不足しています | 運営本部と製品開発本部の間に同席が0件です |

**ID をそのまま画面に出さない。** `person_id` は内部の識別子で、人事担当者は読めない。
`display_name` に直してから出す。`u_089…` のような途中で切った ID は特に読めない。

**「2つ以上」「複数の」「一部の」で止めない。** 数と、可能なら名前を書く。
名前が4つ以上になるなら、部門の内訳（`管理本部 3名・営業本部 2名`）にまとめる。


### 0a. 「1件もない」「一度もない」と書かない

関係の重みが下限（`min_edge_weight`、既定 0.3）に満たない組は、**グラフを作る前に落としている**。
落とした記録があるので、グラフ上で辺がないことを「1件もない」とは書けない。

> 合成データでは、運営本部は他部門と3件の大人数会議に出ていた。そのすべてが下限未満で
> 落ちていたため、グラフ上の辺は0本になる。「他部門の人と一度も同じ会議に出ていません」は
> **事実として誤り**だった。

書けるのは「**継続的と言える接点が残っていない**」まで。
証拠の弱い記録を落としていることも、同じ場所に書く。

`tests/test_report.py::test_report_does_not_claim_a_contact_never_happened` が
「1件もありません」「一度も」「0件です」を全ページで探している。

### 0a2. 説明文に「会議」「同席」と書かない

関係＝会議の同席であることは、概要の「この分析について」と「データ」ページに書いてある。
説明のたびに測り方を言い直すと、読み手は**観測値から意味を自分で組み立てる**ことになる。
説明文・表の見出し・「いまの状態」では、**つながり**と書く。

| ❌ | ⭕ |
|---|---|
| 他の人どうしが会議でつながる経路のうち | 他の人どうしがつながる経路のうち |
| 同席した相手どうしが、互いにどれだけ同席しているか | つながっている相手どうしが、互いにどれだけつながっているか |
| 互いに接点のない複数の集団の会議に出ています | 互いに接点のない複数の集団に入っています |
| その部門の同席のうち、部門の中だけで起きたもの | その部門のつながりのうち、部門の中だけのもの |
| メンバーどうしの同席量と、部門外で会った相手の広さ | メンバーどうしのつながりの濃さと、部門外の相手の広さ |
| 複数の部門の会議に出ていて | 複数の部門とつながっていて |
| ランダムに会っていた場合の割合 | ランダムにつながっていた場合の割合 |
| 直接会った相手の数 | 直接つながっている相手の数 |

**「会議」「同席」を書いてよいのは、何を測ったかを示す4か所だけ。**

| 場所 | 例 |
|---|---|
| 概要の「この分析について」 | その形を会議の同席記録だけから簡易的に測ったものです |
| データページ | 会議イベント 1,719／1on1 の関係 142（2名の会議由来） |
| 各ページの「この指標の限界」 | 集計したのは会議の同席だけ。チャット・メール・立ち話は含まない |
| 打ち手 | 運営本部 との間に、双方の担当者が出る会議を作る |

打ち手だけは、実際に会議を設定したり人を同席させたりする**動作**なので言い換えない。

### 0b. 観測していないことを書かない

観測したのは**会議に同席したかどうか**だけ。
同席から言えないことを書くと、読んだ人が数値を誤って解釈する。

| ❌ | ⭕ | なぜ |
|---|---|---|
| 他に共通の知人がいるのは0% | 両方と同席している別の人がいるのは0% | 社内ならほとんどが知人。数えたのは同席 |
| 部門内コミュニケーション量 | 部門内の同席の重み | 会話も chat も見ていない |
| 仲が良い／信頼関係がある | 1on1 が週1回ある | 関係の質は測っていない |
| 交流が活発 | 部門をまたぐ同席が15件ある | 「活発」は観測量ではない |

### 0c. 利用者が読めない用語を出さない

読むのは人事担当者で、ネットワーク分析もグラフ理論も知らない。

| ❌ | ⭕ |
|---|---|
| ノード／エッジ | 丸／線、人／関係 |
| 被覆率 100% | カレンダーを集計できた人 100% |
| 単一障害点 | 抜けると接点が切れる人 |
| 代替可能性／代替率 0% | 代わりの人がいる相手どうしの組 0% |
| 関節点 | その人を除くと切れる位置 |
| 分析レベル L2（実名） | 氏名の扱い 実名で出す |
| 閾値を超えたもの | 同席が下限を超えた組 |

**残してよい語**は、典拠の用語で、かつ**初出でその場に定義を書いたもの**だけ。
制約・媒介中心性・モジュラリティ・内部密度・外部範囲がこれに当たる。

> ⭕ 他の人どうしが会議でつながる経路のうち、どれだけがその人を通るかを測ります（媒介中心性）
> ❌ 媒介中心性の上位10名です

### 0d. 図と表の説明は「読み方」から書く

読むのは人事責任者で、データ分析者ではない。
**作り方を説明しても、図は読めるようにならない。**
最初の1文で、**数値が大きいと何なのか／どこを見ればよいのか**を書く。

| ❌ 作り方の説明 | ⭕ 読み方の説明 |
|---|---|
| 対角が部門内、それ以外が部門間です。人数の多い部門は合計が大きくなるため、1ペアあたりの値に直しました | **濃いマスほど、その2つの部門の人がよくつながっています。**…**見るのは対角以外のマスで、業務上つながる必要があるのに薄い組**を探してください |
| この割合は部門の人数に左右されます | **「部門の中だけのつながり」が「ランダムならこの割合」を大きく上回るほど、その部門は中で閉じています。** |
| 丸の大きさは部門の人数です。丸にカーソルを合わせると数値が出ます | **右へ行くほど部門外に広くつながり、上へ行くほどメンバーどうしが濃くつながっています。** 右上が効率型、右下がイノベーション型です |
| 参加人数は人数で切らず、連続した関数で重みに反映しています | **参加人数が多い会議ほど、1組あたりを軽く数えています。** 2名で60分の会議を 1.0 として、100名の会議は1組あたり 1on1 の約2万分の1です |

書く順番は3つ。

1. **向きと意味** — 濃い／右／上が何を表すか。`<b>` で囲んで最初に置く
2. **どこを見るか** — 「見るのは対角以外のマスで、…を探してください」
3. **作り方の断り** — 1ペアあたりに直した、人数で補正した、などは最後に1文で

**軸のラベルは、表の列と同じ言葉にする。** 図だけ「外部範囲（広い）→」、
表は「部門外の相手」と書くと、同じものだと分からない。

**色で量を示す図には凡例を付ける。** どの濃さが何を表すのかを、
同じ画面の中で確かめられるようにする。色は**1色だけ**にし、
尺度が違うもの（部門の中と、部門と部門の間）は2色で塗らずに、
片方を灰色の下地にして比較の対象から外す。

| ❌ | ⭕ |
|---|---|
| 濃いマスほど、その2つの部門の人がよくつながっています | **数字が大きいマスほど**、その2つの部門の人がよくつながっています（＋ 0.00〜最大値の凡例） |
| 対角を青、それ以外を緑で塗る | 1色の濃淡で塗り、対角は灰色の下地に置く |

`tests/test_report.py::test_the_heatmap_has_a_legend` が、凡例の有無と色が1色かを見ている。

`tests/test_report.py::test_every_chart_says_how_to_read_it` が、
図のすぐ下の説明が `<b>` で始まっていることを全ページで見ている。

### 1. 主文を先に書く。否定・対比・留保から始めない

| ❌ | ⭕ |
|---|---|
| 部門の優劣ではなく、目的に合っているかを見てください | 納期を守る仕事と新規探索の仕事では、望ましい型が逆になります |
| 問題はその人がかけがえのないことではなく、補う者がいないことです | 同じ接点を持つ人が社内に他にいない場合、その人が異動すると部門間の接点が切れます |
| 接点が必要だとは限りません | 業務上の関連がない部門間なら、同席がなくても支障はありません |
| 数値そのものより、本来つながるべき部門と切れていないかを見てください | 業務上つながる必要がある部門と同席しているかを確認してください |

`does_not_mean` のように「〜ではない」が必要な場でも、**その後に何なのかを書く**。

> ❌ 人気や好感度ではない。また役職の高さとも一致しない
> ⭕ この数値は好感度を測っていない。役職の高さとも一致しない

### 2. 比喩と抽象語を使わない。数値か具体的な動作で書く

| ❌ | ⭕ |
|---|---|
| 知見が内部に滞留している可能性があります | 部門内だけの会議が部門外との会議の13.2倍あります |
| 情報の流れを支えている人物 | 複数の部門の会議に出ていて、同じ接点を持つ人が社内に他にいない人 |
| 外部リソースにも手が届く | 部門外にも重複しない接点がある |
| 部門の壁が厚い | 部門をまたぐ同席が少ない |
| 全社会議がネットワークを埋め尽くす | 100名の会議は1ペアあたりの重みが1on1 の約2万分の1になります |
| 狭く密な人間関係に縛られず | 互いに接点のない複数の集団の会議に出ている |

禁止する語の例（`check_wording.py` が検出する）:
滞留／手が届く／壁が厚い／埋め尽くす／縛られる／支えている／流れが切れる／
光を当てる／浮かび上がる／寄り添う／紐解く／輪郭／羅針／鍵を握る

### 3. 曖昧な名詞化とぼかしを使わない

| ❌ | ⭕ |
|---|---|
| 外部との接点を複線化する | 社外との会議に2人目を同席させる |
| 情報の棚卸しをする | この部門が持っているデータを一覧にし、他部門が使えるものがないか確認する |
| 内部密度を下げる工夫が要る | メンバーを入れ替えて同席の偏りを減らす |
| 後継者育成計画を立てる | この人が出ている部門横断の会議に、同じ部門の別の人を同席させる |
| 傾向として読んでください | 個人の順位は数位ずれます。上位5名・下位5名という範囲で見てください |
| 断定せず確認の起点としてお使いください | 本人または上長に確認してください |
| 変革推進の起点として検討する | 新しい方針を周知するとき、この人に最初に説明する |

**打ち手は、明日その人が実行できる粒度まで下ろす。**

### 4. 対句・体言止め・ダッシュで印象づけない

| ❌ | ⭕ |
|---|---|
| 接触数の割に到達力が高い——見落とされやすい真のインフルエンサー | 接触数の順位より招集の到達力の順位が高い人です |
| 偶然の同席とは質が違うため、別に見ます | 参加者が2名の会議だけを抽出した結果です |
| 同じ2変数を逆向きに読みます | 内部密度と外部範囲の2つで分類します |

## 見出しとラベル

- 見出しは内容を示す。「まず見るところ」ではなく「概要」。「要点」ではなく「数値が大きかったもの」
- カードのラベルは測ったものを書く。「サイロ化が警戒域の部門」ではなく「部門内の会議が5倍を超えた部門」
- 「見落とされやすい influencer」のような英語混じりの飾りを使わない

## 典拠の扱い

書籍や論文の主張は、**自分の判断と区別して書く**。

> ⭕ 研究では、5倍を超えると有害な水準としています
> ⭕ 研究では、効率型の特徴を持つ部門をイノベーションに充てると最も失敗しやすいとしています
> ❌ 5倍を超えると有害なレベルとされます（誰がそう言っているのか不明）

### 画面には「典拠」と書かない

「典拠」は日常で使う語ではない。設計とコードの中では使ってよいが、
**レポートに出す文面では次の2つに置き換える**。

| 画面に出す語 | 使う場所 |
|---|---|
| 研究 | 文の中で主張の出どころを指すとき（「研究では、…としています」） |
| 出典 | 書誌そのものの見出しやラベル（「この数値の出典:」「分析ごとの出典」） |

- その分析のページで最初に出るときは「元になった研究」と書き、どの研究かが分かるようにする
- `tests/test_report.py::test_metric_pages_point_to_the_sources_page` が
  「この数値の出典」を全ページで探している

### 書誌は `src/relana/core/citations.py` に1か所でまとめる

コードの各所に文字列で書くと、版が変わったときに直し漏れる。
新しい指標を足したら、ここに次の5つをそろえて登録し、`BY_FEATURE` にページを対応させる。

| 項目 | 書くこと |
|---|---|
| `authors` | 著者名。日本語文献は訳者ではなく著者 |
| `year` | 発行年 |
| `title` | 論文名・書名 |
| `where` | 掲載誌・巻号・ページ、または出版社 |
| `basis` | **この OSS がそこから何を取ったか。** 文献名だけでは何が典拠なのか分からない |

`OWN_CHOICES` には、**典拠にないのに自分で決めたこと**を書く。
閾値、補正、グループ分けの基準は、たいてい典拠にない。混ぜて書くと、
読んだ人が「研究でそう決まっている」と誤解する。

> ⭕ I/E 比は部門の人数に左右されるため、ランダムに会っていた場合の比を併せて出している。この補正は研究にない
> ❌ （補正の説明だけ書いて、典拠にあるかのように見せる）

### 書誌は出典ページ（`sources.html`）にだけ置く

指標ページの中に著者名・掲載誌・巻号を並べると、数値と打ち手の間に文献が挟まって読みにくい。
指標ページには**短い名前の1行**だけを置き、定義は出典ページで読ませる。

> ⭕（指標ページ）この数値の出典: Burt（1992）。定義と、研究にない部分を見る → 出典
> ❌（指標ページ）Ronald S. Burt（1992）Structural Holes: The Social Structure of Competition, Harvard University Press…

出典ページは3つに分ける。

1. **分析ごとの出典** — ページ単位で、何をどの文献から取ったか＋`OWN_CHOICES`
2. **文献** — 著者・年・題名・掲載先と、使っているページ
3. **この OSS が自分で決めたこと** — どの文献にもないもの

`tests/test_report.py` が、指標ページに書誌が入っていないこと・出典ページに全文献が
あること・`OWN_CHOICES` が出ていることを見ている。

専門用語（サイロ、制約、媒介中心性、モジュラリティ）は典拠の用語なので使ってよい。
ただし**初出で何を測ったものか書く**。

> ⭕ 同席相手どうしが互いに同席していない度合いを測ります（制約）

## 数値の書き方

- 母数を書く。「部門内2位」ではなく「20名中2位」
- 丸める。`0.17168` ではなく `0.172`。パーセンタイルは整数

### 読み手が思い浮かべられる単位に直す

比・1人あたりの小数・単位のない指標値は、**正しくても頭に入らない**。
同じことを、**人数・件数・割合**で言い直してから出す。

| ❌ そのままの指標値 | ⭕ 言い直したもの |
|---|---|
| 石井089 を除くと、管理本部 6名 が残り77名と会議でつながらなくなります | 管理本部 6名 が会議で同席している相手は、この6名と 石井089 だけです |
| 部門内だけの会議が部門外との会議の 3.67倍 あります | 同席のうち、79% が部門の中だけです |
| ランダムに会っていた場合の 29.3倍 | 同じ人数の部門がランダムに会っていれば 11% です |
| 部門外と同席した相手が1人あたり 0.10 名 | 部門外で同席した相手は、全員合わせて 1名 |
| 内部密度 13.1（中央値 13.9） | メンバーどうしの同席量は、全部門の中央値の 0.94倍 |
| 重複しない割合 0.53（中央値 0.86） | 部門外の相手1人に、平均 1.9名 のメンバーが会っています |
| 制約 0.085 | 17名と同席していますが、その中で互いに同席している組は 13% です |

直し方は3つ。

1. **比を割合にする。** `a/b` が 3.67 なら、`a/(a+b)` = 79% と書く
2. **1人あたりの小数を実数に戻す。** 0.10名／人 × 10名 = 1名
3. **読めない語をやめる。** 「残り77名と会議でつながらなくなる」の
   「残り77名」と「つながらなくなる」は、読み手が頭の中で組み立て直す必要がある。
   「社内の他の人と会議で接点がなくなる」と書く

典拠の指標値（制約、媒介中心性、I/E 比）は**表に残してよい**。
順位の根拠になるため、消すと検算できなくなる。
ただし**文章では言い直したほうを先に出す**。

### 0e. 人を指す名前を付けたら、冒頭で何を数えたかを書く

画面に出す3つの人の分析は、**その人が置かれている位置の呼び名**で名付けている。
人事担当者が目次を1回読んで何の話か分かることを優先した結果で、
測っているのは**つながりの形**であり、人の能力ではない。

名前だけを置くと能力の評価に読め、`does_not_mean`（人事評価に使えない）と矛盾する。
**ページの冒頭に、何を数えてその名前を付けたかを必ず書く。**

| 画面の名前 | 冒頭に必ず書くこと |
|---|---|
| インフルエンサー | 順位は経路の通り方だけで付けていること。同僚からの評価と人気は入っていない |
| ハブとなっている人 | ハブはその人が持っている接点の位置を指すこと。仕事の出来は測っていない |
| 発想の起点となる人 | 順位は位置で付けていること。実際に出した発想の数は数えていない |

> ⭕ つながっている相手どうしが、互いにどれだけつながっているかを数えます。……順位はこの位置で付けています。その人が実際に出した発想の数は数えていません。
> ❌ （名前だけ出して、何を数えたかを書かない）

見出しの問いも同じで、観測していないことを問いにしない。

| ❌ | ⭕ |
|---|---|
| よいアイデアを思いつくのは誰か | 新しい発想が出やすい位置にいるのは誰か |

**ページ名・目次・概要のカード・図の軸は、同じ語でそろえる。**
片方だけ変えると、同じものを指していることが読み取れない。

## ❶〜❻ をレポートに出さない

番号は典拠（第5章）の章立てで、**設計とコードの中だけで使う識別子**。
読む人には何の番号か分からないので、画面には出さない。

| コード内（残してよい） | 画面（出す名前） |
|---|---|
| ❶ 発想力 / constraint | 発想の起点となる人 |
| ❷ 影響力 / betweenness | インフルエンサー |
| ❸❹ 効率性・イノベーション / density_x_range | 部門の型 |
| ❺ サイロ / ie_ratio | 部門のつながり |
| ❻ 脆弱性 / node_criticality | ハブとなっている人 |

`tests/test_report.py::test_report_has_no_circled_numbers` が全ページを見ている。

## 概要ページに書くこと

利用者は**このレポートが何をしている分析なのかを知らない**。
次の順に置く。順番を入れ替えない。

1. **この分析について** — 何をどう測ったか。結果より先に置く
2. **この分析で分かること** — 5つの分析それぞれの名前と、この組織での結果

**概要にはこの2つ以外を置かない。**
打ち手・図・一覧はそれぞれのページにある。概要にも並べると同じものが2か所に出て、
読む人は別の話が2件あると受け取る。概要は**どのページを開くかを決めるための1枚**にする。

**分析をまたいだ総括の節（「この期間で目立つこと」など）も置かない。**
指標の単位が違うので順位を付けられず、固定した順で並べることになる。
結局どの行も「この分析で分かること」に出る内容と同じになる。

### 1. この分析について

ネットワーク分析を知らない人が、結果から読み始めると、
「会議の同席だけで何が言えるのか」が分からないまま数値を受け取ることになる。
**2行で止める**。細かい内訳はデータページにある。

| 項目 | 書くこと |
|---|---|
| データ | 取っているもの**と、取っていないもの**（会議の中身・件名・場所、チャット、メール） |
| 分析内容 | 5つの分析の名前 |

数え方（同席を関係として数えること、人数の多い会議を軽くすること）は
**ここに書かない**。概要の冒頭1文とデータページにあり、3行目にすると
読み始める前に読むものが増える。

### 2. この分析で分かること

指標名と数値だけを並べても、何が分かるのかが伝わらない。
分析1つにつき、次の4つを**1枚のカード**に上から並べ、5枚を横に並べる。
カードは、5つを一度に見渡せる長さに保つ。結果を2本以上出すと縦に伸びて見渡せなくなる。

1. **分析の名前** — 「部門のつながり」。目次・「見るもの」・移った先のページの見出しと**同じ語**にする
2. **問い** — **人事が判断したいこと**を問いの形で1行。「部門間のつながりを作っているキーパーソンは誰か」
3. **この組織での結果** — 氏名・部門名と数値の入った文を1本（`src/relana/core/summary.py` が選ぶ）
4. **件数** — 「該当は6名です」のように、そのページに何件あるか

**2に数え方を書かない。** 「その人が抜けたとき、社内から切り離される人が出るかを
調べます」を読んでも、**どの分析を開けばよいかは決められない**。
何をどう数えたかは、移った先のページの冒頭に置く。

件数だけのカード（「ハブとなっている人 6」）は、2〜4が無いので置かない。

**カードごとに別の見出しを付けない。** 「どの部門が内向きになっているか」のような問いを
見出しにすると、目次の「部門のつながり」と同じものを指しているかどうかが分からない。
問いは見出しの下（2行目）に置き、**移った先のページの冒頭（`_page_head` の2つめの
引数）とそろえる**。カードで見た問いと別の問いがページに出ていると、
同じ分析を開いたのかどうかが分からない。

`tests/test_report.py::test_index_explains_what_each_analysis_counts` が、
5枚の見出しが分析名と一致していることを見ている。

#### カードの中で同じことを2回書かない

カードは灰色の小さな文字が続くので、1文でも増えると読まれなくなる。
**結果の1行目に書いたことを、続く説明でもう一度書かない。**

| ❌ 1行目を言い直している | ⭕ 1行目にないことだけ書く |
|---|---|
| （1行目）運営本部の18名には、部門の外とのつながりがほとんどありません<br>（説明）社員100名のうち18名が、マーケティング本部、営業本部…のどこともつながっていません | （説明）つながりが残っていない相手は マーケティング本部、営業本部… です |
| （1行目）石井089 が異動すると、管理本部の6名は社内から孤立します<br>（説明）この6名と社内の他の77名をつないでいるのは、石井089 ひとりです。後任を立てるときは、この人たちとの関係をどう引き継ぐかが問題になります | （説明）この6名を社内の他の77名とつないでいるのは、石井089 ひとりです。後任には、この関係の引き継ぎが要ります |

- 説明は**2文まで**。1文目に数値、2文目にそれが何を意味するか
- 研究の文は「研究は、この形が新しい発想を生むとしています」のように短くする。
  研究が何を根拠にそう言っているかは、出典ページにある
- 件数の行は1つだけにする。「基準を超えた部門は2つです。継続的な接点が残っていない
  部門の組は4組です」のように2つ並べない

#### 結果の文で測り方をなぞらない

**結果の文に「会議」「同席」「出席」という語を使わない。**
何をどう測ったかは、移った先の各ページの冒頭に書いてある。
ここで測り方をもう一度なぞると、読み手が**観測値から意味を自分で組み立てる**ことになる。
組み立てた結果だけを書く。

| ❌ 測り方をなぞる | ⭕ そこから言えること |
|---|---|
| 運営本部（18名）が会議で同席しているのは、運営本部の人だけです | 運営本部の18名には、部門の外とのつながりがほとんどありません |
| 管理本部 6名 が会議で同席している相手は、この6名と石井089 だけです | 石井089 が異動すると、管理本部の6名は社内から孤立します |
| 管理本部（12名）の同席のうち、79% が部門の中だけです | 管理本部は、人のつながりの8割が部門の中で閉じています |
| サポート（10名）が部門外で同席した相手は、全員合わせて1名です | サポート（10名）は、部門の外とのつながりがほとんどありません |

- 結果の1行目には必ず**数値と固有名詞**を入れ、**その1行だけで読み切れる文**にする
- 1行目の割合は「8割」、続く説明の割合は「79%」。先に出すほうは1回読んで分かることを優先する
- 説明の最後に、**それが何を意味するか**を1文で書く
  （「他部門の動きは、この部門には届きにくい状態です」）

`tests/test_report.py::test_examples_do_not_restate_how_it_was_measured` が見ている。

#### 細いところだけを並べない

欠けているところだけを並べると、読んだ人は**何を保てばよいか**が分からない。
打ち手には「いまの型のまま仕事を割り当てる」というものもあり、
そのためには、どの部門と誰がその型なのかを先に知る必要がある。

| 出すもの | 例 |
|---|---|
| 研究が「この形なら成果が出やすい」としているもの | アーキテクチャ（6名）は、新しいことを探す仕事に向いた形です |
| 他と比べて差が大きく、細くなっているもの | 運営本部の18名には、部門の外とのつながりがほとんどありません |

- 同じ分析に両方あるときは、**成果が出やすいとされている形を出す**（`ORDER` で先に置く）
- その詳細には**必ず研究を添える**。良い形だと決めているのは研究であって、この OSS ではない
- 同じ人が両方に出てよい。周知に使える位置の人が、抜けると接点が切れる人でもある
- 見出しに「問題」「課題」「リスク」を使わない。
  担っている仕事によっては、そのままで支障がないものが含まれる

`tests/test_report.py::test_examples_show_strengths_as_well_as_gaps` が見ている。

#### 分析をまたいだ順位を作らない

I/E 比は「何倍」、切り離される人数は「何名」で単位が違う。
足したり重み付けしたりしても意味のある量にならず、重みしだいで順位が変わる。
**分析ごとに区切って出し、同じ分析の中だけで順を固定する。**
並べ方の説明は書かない。各行がそれだけで読めるなら、順位の根拠を読む必要がない。

## 出力を読み返すときの点検

`snapshots/demo/report/*.html` を開き、**1ページずつ**次を確認する。
`check_wording.py` はこの4つのうち1と2の一部しか検出できない。

### 1. その文だけ読んで、誰のことか分かるか

集合に言及している文を全部拾い、中身が書いてあるか見る。

- 「2つ以上に分かれる」→ どの集団が分かれるのか氏名か部門の内訳が出ているか
- 「N名が孤立する」→ その N 名が誰か出ているか
- 「接点が不足」→ どの部門とどの部門の間か出ているか

### 2. 画面に内部の識別子が出ていないか

`u_001`、`ext:example.com`、`u_089…` のような文字列を探す。
1件でもあれば `display_name` に直す。社外は `ext:` を外してドメインだけを出す。

### 2b. レポートが自分の信頼度を採点していないか

「信頼度 高い」「このスコアは判断に使える」のような自己採点は出さない。
**何から数えたか**（取得できた会議の同席）を各ページに書いてあれば、
読む人はそれを踏まえて読む。その上で指標ごとに点を付けても、次の行動が変わらない。

集計した人数のような**事実**は残す。判定に変えない。

> ⭕ 集計できた人 100名（同席が1件以上あったのは 100%）
> ❌ 6つの指標はいずれも信頼度が高いです。個人ごとのスコアを判断に使える。

**例外**は、読み方が実際に変わるとき。部門をカレンダーから推定した場合は、
推定した区分で区分間の往来を測ると循環論法になるため、その旨を書く。

### 3. 全行が同じ値の表を出していないか

表を見て、**ある列が全行同じ値なら、その表は情報を持っていない。**
1行の文に畳むか、値が割れたときだけ表にする。

> 例: 被覆率100%のとき、信頼度の表は6行とも「高い／個人ごとのスコアを判断に使える」になる。
> 「6つの指標はいずれも信頼度が高いです」の1行にする。

### 3b. 全員に同じ打ち手を出していないか

同じ文面が、そのページの対象の半分を超えたら、読者は打ち手ごと読み飛ばす。
**状況が違うのに処方箋が同じなら、状況を見ていないということ。**

> 例: 他部門との同席が0件の部門と、1部門とだけ0件の部門に、
> 同じ「全部門のマネジャーが集まる会議を作る」を出していた。
> 前者は「どの部門とつなぐかを決める」、後者は「その部門との会議を作る」に分ける。

打ち手は、その対象の状況から組み立てる。少なくとも次を見分ける。

- 0件なのか、量が少ないのか
- 相手が社内か社外か（社外の窓口が1人なのは珍しくない）
- 引き継ぐ相手がいるか
- その人の会議時間が実際に多いか（中央値と比べて書く）

### 3c. 同じ事実を2ページで書いていないか

同じ事実が2か所に出ると、読者には**別の問題が2件ある**ように見える。
片方に書き、もう片方からは**リンクで送る**。

> 例: 他部門との同席が0件の部門は、「部門のつながり」に書く。
> 「発想の起点となる人」では同じ話を繰り返さず、「その扱いは部門のつながりに書いています」と送る。

### 3d. 計算できない値を数値のように出していないか

分母が0なら比は計算できない。`∞` は数値に見えるので使わない。
**`-` を出し、文章では「0件です」と事実を書く**。

### 3e. 中央値で切った分類を、そのまま断定していないか

中央値で2つに割ると、**中央値のすぐ近くの部門はわずかな差で別の型に移る**。
どちらの軸も中央値から2割の中に入るものには、型を付けない。
「この2つの値では判定できません」と書き、打ち手も出さない。

### 4. 打ち手の前に「いまの状態」が書いてあるか

打ち手だけを並べると、なぜそれをするのかが分からない。
**何が起きているかを数値で先に書く**。`_actions_block(actions, problem=...)` の
`problem` がそれに当たる。

```
いまの状態
  管理本部（12名）は、部門内だけの会議が部門外との会議の 3.67倍 あります。
  同じ人数の部門がランダムに会っていた場合の 29.3倍で、判定の基準（21.1倍）を
  超えています。同席した会議が0件の相手は 運営本部 です。

打ち手
  ・他部門との合同会議を設定する
  ・…
```

書き方の条件は3つ。

1. **数値を入れる。** 「サイロ化しています」ではなく「3.67倍」「21.1倍」
2. **打ち手が指す事実を書く。** 後継者を同席させる打ち手なら、いまの候補と不足数を書く
3. **上の節と同じことを繰り返さない。** カードの冒頭文や別の節にある内容は書かない

### 打ち手の見出しは「〜したい場合」にする

**その状態を変えるべきかどうかは、その部門や部門が担っている仕事で決まる。**
この OSS は仕事の中身を観測していないので、変えるべきだと書ける根拠がない。
見出しを「打ち手」で止めると、変えるのが前提に読める。

| ❌ | ⭕ |
|---|---|
| 打ち手 | この部門と他部門の往来を増やしたい場合 |
| 打ち手 | この人が抜けても接点が残るようにしたい場合 |
| 打ち手 | 部門外との接点を増やしたい場合 |

ページの冒頭にも、**その状態のままでよい場合**を1文で書く。

> ⭕ 業務上の関連がない部門どうしなら、同席がなくても支障はありません。打ち手は、往来を増やしたい場合のものです。
> ⭕ 決まった相手と深く進める仕事なら、制約が高くても支障はありません。

`tests/test_report.py` が、打ち手の枠の数と「いまの状態」の数が一致すること、
その中に数値があること、見出しが条件つきになっていることを見ている。

### 打ち手に「どの数値になれば成功か」を書かない

ネットワークに**正しい形はない**。「3か月後に再測定し、0% → 100% になっていることを
確認する」と書くと、100% が正解だと決めつけることになる。

書けるのは**やったかどうか**までで、**どの値になるべきか**は書けない。
試算（`simulate`）を出すときも、「この打ち手を取ると数値はこう動く」までにとどめ、
そこへ行くべきだとは書かない。

| ❌ | ⭕ |
|---|---|
| 3か月後に再測定し 0% → 100% を確認する | 渡辺096 を 1件の接点に同席させる（代わりの人がいる相手どうしの組 0% → 100%） |
| この部門の I/E 比を 5.0 以下にする | 同席が0件の4部門のうち、業務上つながる必要がある部門を決める |

### 1人に対する打ち手は1か所にまとめる

同じ人が「インフルエンサー」「ハブとなっている人」「発想の起点となる人」に別々に出る。
各ページだけを読むと、**その人に対して結局何をするのかが分からない**。

まとめる場所は**ネットワーク図の詳細パネル**（`src/relana/report/graph_data.py`）。
人をクリックすると、その人が持つ役割と打ち手がまとめて出る。

- 役割をまたいで**同じ文面を2回出さない**（重複を取り除く）
- 多すぎるときは上から数件に絞る

`tests/test_report.py::test_one_person_has_their_actions_in_one_place` が、
役割を複数持つ人それぞれについて、重複のない打ち手が出ていることを見ている。

### 5. 数値のとなりに、次にやることが書いてあるか

各指標ページに `class='actions'` の枠があり、**そのページの数値に対応した**打ち手が入っているか。
打ち手が全ページ同じ文面になっていたら、指標ごとに書き直す。

## 指標を追加するときのチェック

新しい指標の `interprets_as` / `does_not_mean` / `caveats` / `suggested_actions` は、次を満たす。

| 項目 | 書くこと |
|---|---|
| `interprets_as` | **何を数えたか**。「〜の可能性」で終わらせない |
| `does_not_mean` | この数値で判断してはいけないこと。「〜ではない」の後に何なのかを書く |
| `caveats` | 母数、観測していないもの、順位が変わる条件 |
| `suggested_actions` | 主語と動作。明日実行できる粒度 |

## 組織の区分は「部門」1階層だけ

名簿に部門（dept）とチーム（team）の2列があっても、**画面に出すのは1階層だけ**にする。
分析も表示も `team or dept` の1つの区分で行う。

> 本部と課を同時に画面に出すと、読む人はどの数値がどちらの話かを決められない。
> 「部門のつながり」と「部門の型」が別の粒度を指していると、2つの結果が結び付かない。

画面に「チーム」という語を出さない。もとの dept はネットワーク図で
**色を同系統にまとめる**のにだけ使う（グラフのノード属性 `family`）。
