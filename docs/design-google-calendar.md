## 1. なぜカレンダーだけで成立するか

会議の**同席関係**から重み付きグラフを構築すれば、6つの構造的特徴はすべて計算できる。

| 特徴 | カレンダーのみでの算出 |
|---|---|
| ❶ 発想力 | 会議ネットワーク上の constraint（複数クラスタを跨いで会議に出ているか） |
| ❷ 影響力 | 無向グラフ上の **重み付き媒介中心性**（他の人どうしの経路がどれだけその人を通るか） |
| ❸ 効率性 | チーム内会議の密度 ＋ チーム外会議の広がり |
| ❹ イノベーション | 同上（内部密度を逆向きに読む） |
| ❺ サイロ | 部門内会議 ÷ 部門間会議（I/E 比） |
| ❻ 脆弱性 | 複数部門の会議を横断する人物、外部ドメインへの単一接点 |

**主催者は使わない。** 代理設定や、定期会議の作成者が残ることで記録が汚れる。
合成データで測った結果、主催するかどうかはマネジャーかどうかでほぼ決まっていた
（r = +0.927。マネジャー12名の主催量は中央値48.9、非マネジャー88名は中央値0.0）。
**組織図以上の情報を持たないため、分析に使わない。**

## 2. 全体フロー

```
persons.csv （メールアドレス＋部門。利用者が用意）
     │
     ▼
 ① 認証        relana connect google      OAuth（§3）
     │
     ▼
 ② 収集        relana collect --source gcal
     │          各メンバーの calendar.events.list を取得

     ▼
 ⑤ 指標計算    6特徴（§7）
     ▼
 ⑥ 出力        findings.json / report.html / ロール別出力
```

## 3. 認証設計

### 3.1 既定方式: 利用企業が自社に内部用OAuthクライアントを作成（方式b）

公開クライアントの審査要件を回避でき、手順はエージェントが案内できる。

```
relana connect google
  → エージェントが手順を表示（GCPコンソールの画面名・ボタン名まで）
     1. プロジェクト作成
     2. Google Calendar API を有効化
     3. OAuth同意画面を「内部」で作成   ← 内部ならアプリ審査が不要
     4. OAuthクライアントID（デスクトップアプリ）を作成
     5. client_id / client_secret を relana に貼り付け
  → ブラウザが開く → 「許可」
  → トークンをOSキーチェーンに暗号化保存
```

### 3.2 必要スコープ（最小限）

| スコープ | 用途 | 必須 |
|---|---|---|
| `calendar.readonly` | 他メンバーのカレンダー読み取り | ✅ |
| `admin.directory.user.readonly` | メンバー一覧の自動取得 | 任意（persons.csv で代替可） |

### 3.3 フォールバック（FR-1.18.2）

| 優先 | 方式 | 条件 | 取得範囲 |
|---|---|---|---|
| 1 | 内部用OAuthクライアント（上記） | 社内共有設定が「すべての情報を共有」 | 読めたカレンダー |
| 2 | **サービスアカウント＋ドメイン全体の委任** | 管理者が設定（10分程度） | **全員。共有設定に依存しない** |
| 3 | 管理コンソールの監査ログCSV | 管理者がエクスポート | 全員（粒度は落ちる） |

> **社内共有設定が「予定の有無のみ」の組織では方式1が機能しない**（参加者が取れない）。
> その場合は方式2を案内する。`doctor` が被覆率から自動判定して提案する。

### 3.4 ★実装前の必須検証 — `scripts/verify_calendar_access.py` で実行する

```bash
.venv/bin/python scripts/verify_calendar_access.py \
    --client-secrets <JSON> --colleagues a@example.co.jp,b@example.co.jp
```

数名分を読むだけで本番収集は行わない。結果は `verify-report.json` に残る。


| # | 検証項目 | 判定基準 |
|---|---|---|
| V1 | 一般ユーザーのトークンで他メンバーの `events.list` が成功するか | 200応答が返る |
| V2 | その応答に `attendees` が含まれるか | **含まれなければ方式1は不成立** |
| V3 | 「内部」同意画面でアプリ審査なしに運用できるか | 警告画面なしで認可完了 |
| V4 | 100カレンダー×90日の所要時間とAPI消費 | 10分以内・クォータ内 |

## 4. 収集設計

### 4.1 対象者の決め方 — 名簿は利用者に用意させない

**利用者はカレンダーを連携するだけでよい。** 名簿・部門・チームはカレンダーから推定する（§4.2）。
推定結果は下書きとして CSV に書き出され、利用者は必要に応じて修正できる。

```
relana infer-org --interactions ... -o persons.csv   # 下書きを作る
（利用者が dept 列を確認・修正）
relana snapshot create 2026Q1 --interactions ... --persons persons.csv
```

`--persons` を省略すればそのまま推定値で分析できる（サイロ診断に注記が付く）。

名簿を自前で用意する場合の形式:

```csv
person_id,email,display_name,dept,team,role,hired_at,left_at,is_bot,is_external
u_001,tanaka@example.co.jp,田中,製品開発本部,パッケージング,マネジャー,2016-04-01,,false,false
u_002,sato@example.co.jp,佐藤,製品開発本部,パッケージング,エンジニア,2021-10-01,,false,false
```

### 4.2 組織構造の推定（`core/org_inference.py`）

#### 設計上の注意: 循環論法を避ける

「よく話すまとまり」を部門と定義して「部門間であまり往来がない」と測ると、**定義上必ずそうなる**。
❺サイロ診断が無意味になるため、**汎用のコミュニティ検出を第一手段にしない。**

代わりに、カレンダーにしか現れない**会議の設計そのもの**を読む。これは会話量の多寡とは独立した情報になる。

| 推定するもの | 使う痕跡 | 強さ |
|---|---|---|
| **チーム** | 定期的なグループ会議（3〜15名）の固定メンバー。毎週同じ顔ぶれが集まる会議はほぼ確実にチーム定例 | ★最強 |
| **上司** | 定期1on1 の非対称な星形。A が B・C・D と1on1 を持ち、B・C・D 同士は持たない | ★強い |
| **部門** | マネジャーが複数集まる定期会議（部門定例）。**全社会議は除外する**（全マネジャーが出るため全チームが融合する） | 中 |
| （最後の手段） | チーム間の接触量によるコミュニティ検出。上記で何も得られないときだけ使う | 弱い・循環のおそれ |

#### 合成データ（100名・12チーム・5部門）での実測

| 推定対象 | 結果 |
|---|---|
| 人数 | 100/100 |
| **チーム** | **ペアワイズ精度 1.000 / 再現率 1.000**（12チーム、未割当0名） |
| **上司** | **12/12 的中、誤検出0** |
| **部門** | ペアワイズ F1 ≈ 0.82（5部門を正しく5個として検出） |

部門の誤りは示唆的で、**部門を跨ぐ橋渡し役（アルビンド）がいるチームは、その相手部門に吸い寄せられる**。
これは推定の限界であると同時に、利用者が修正すべき箇所が明確であることも意味する。

#### 推定値のまま分析した場合

- `config.analysis.groups_source = "inferred"` が記録される
- ❺サイロの全 finding に**循環論法の注記が自動で付く**
- CLI が「部門を修正することを推奨」と警告する

> **チームと上司の推定は実用水準にある。部門だけが下書きである。**
> この非対称性を利用者に正しく伝えることが設計上重要。

### 4.2 API 呼び出し

```
GET /calendar/v3/calendars/{email}/events
  timeMin        = 窓の開始（RFC3339）
  timeMax        = 窓の終了
  singleEvents   = true      ← 定期会議を各回に展開する
  maxResults     = 2500
  fields         = items(id,iCalUID,start,end,organizer(email),
                         attendees(email,responseStatus,resource,self,organizer)),
                   nextPageToken
```

**`fields` による取得項目の明示的な絞り込みが、FR-1.5（本文非取得）の実装そのもの。**
`summary`（会議タイトル）・`description`・`location`・`conferenceData`・`attachments` は**要求しない**。

- バッチリクエストで並列化。100名 × 90日で数百リクエスト、**数分で完了する見込み**
- 429/5xx は指数バックオフ。チェックポイントを保存し中断・再開可能（FR-1.7）
- 読めなかったカレンダー（共有不可・退職者）はスキップして `collection_report` に記録

## 5. 正規化 — カレンダー固有の処理

**ここが分析品質を決める。** 素のカレンダーデータをそのまま使うと結果が壊れる。

### 5.1 除外ルール（順に適用）

| # | 対象 | 処理 | 理由 |
|---|---|---|---|
| R1 | **会議室・備品リソース** | `attendees[].resource == true` を除去 | Google では会議室が参加者として入る。**除去しないと会議室が最強のハブになる** |
| R2 | **ドメイン外の参加者** | `is_external` として分離 | 個人としては集計せず、❻の外部単一接点検出に使う |
| R3 | **辞退者** | `responseStatus == "declined"` を除去 | 実際に同席していない |
| R4 | **参加者2名未満** | イベントごと除外 | 自分のブロック・休暇・リマインダ |
| R5 | **大人数会議** | **除外しない。** 参加人数を連続関数で重みに反映する（§5.2） | 3名と10名は性質が違う。閾値で切ると不連続・恣意的になる |
| R6 | **終日イベント** | 既定で除外 | 休暇・記念日。会議ではない |
| R7 | **`persons.csv` に無いメンバー** | 外部扱い | 退職者・ゲスト |
| R8 | **重複イベント** | `iCalUID` で排除 | 同じ会議が参加者の人数分だけ取得される |

> **R1 は必須。** 会議室を除去しないと、会議室が最強のハブノードになる。
> 大人数会議の影響は R5 ではなく **§5.2 の重み関数と §6.3 の辺閾値**で扱う。

### 5.2 参加人数の扱い — 閾値ではなく連続関数で

**方針: 「11人以上は除外」のようなハード閾値は使わない。** 3名と10名では会議の性質がまったく違い、
10名と11名の間に断絶があるわけでもない。**参加人数 n を連続変数として重みに織り込む。**

#### なぜ単純な 1/(n-1) では足りないか

| 課題 | 内容 |
|---|---|
| **時間分割だけでは不十分** | `1/(n-1)` は「1人が n-1 人に時間を分ける」という分割の論理（Newman の共著ネットワークと同じ）。だが会議には**もう一つの効果**がある |
| **対話 → 一方向への相転移** | 少人数の会議は全員が相互に話すが、人数が増えるとある時点で**発表と傾聴**に変わる。2人の参加者が実際には一言も交わさない状態になる。これは分割では表現できない |
| **構造の破壊** | n=100 の全社会議は 4,950 ペアを生み、**グラフを完全グラフ化して構造的特徴そのものを消す**。重みが小さくても辺が存在すること自体が ❶制約 や ❺モジュラリティ を壊す |

#### 採用する重み関数

**2つの効果を分けてモデル化する。**

```
w_size(n) = σ(n) / (n - 1)

  σ(n) = 1 / (1 + exp((n - n₀) / k))      ← ロジスティック減衰
         n₀ : 会議が「対話」から「一方向の情報伝達」に変わる人数（既定 10）
         k  : 相転移の滑らかさ（既定 3）

  1/(n-1) : 時間分割の効果（理論的根拠あり）
  σ(n)    : 対話→一方向の相転移（経験的に導入）
```

#### 1on1 を 1.0 としたときの相対重み（n₀=10, k=3）

| 参加人数 n | 相対重み | 1on1 何回分か | 会議の性質 |
|---|---|---|---|
| **2（1on1）** | **1.000** | 1回 | 最も強い関係のシグナル。意図的な二者関係 |
| 3 | 0.487 | 約 1/2 | 密な小グループ。全員が相互に発話 |
| 4 | 0.314 | 約 1/3 | 同上 |
| 5 | 0.225 | 約 1/4 | 作業チーム |
| 6 | 0.169 | 約 1/6 | 同上 |
| 7 | 0.130 | 約 1/8 | 発話の偏りが出始める |
| 8 | 0.101 | 約 1/10 | チーム定例 |
| **10** | **0.059** | 約 1/17 | ★相転移点（σ=0.5）。対話と伝達の境目 |
| 12 | 0.033 | 約 1/30 | 情報共有が主 |
| 15 | 0.012 | 約 1/82 | ほぼ一方向 |
| 20 | 0.0019 | 約 1/516 | 説明会 |
| 30 | 0.00005 | 約 1/21,000 | **実質ゼロ** |
| 100（全社） | ≈ 0 | — | **実質ゼロ** |

> **ハード閾値が不要になる。** n=30 以上は関数が自動的にほぼゼロにするため、
> 「11人で切る」という恣意的な線を引かなくてよい。不連続点がないので、
> 会議が10人から11人に増えただけで結論が変わる、という不安定さも消える。

#### n₀ の調整 — 組織ごとに違ってよい

`n₀` は「**この組織では何人を超えると会議が一方向になるか**」という解釈可能なパラメータ。

| 組織の性質 | 推奨 n₀ |
|---|---|
| 議論重視・フラット・少人数文化 | 12〜15（大きめの会議でも対話が成立する） |
| 標準 | **10（既定）** |
| 報告型の会議が多い | 7〜8 |

- **累積効果を忘れないこと**: 10名定例に四半期13回出席 = 13 × 0.059 = **0.77**（1on1 約0.8回分）。
  単発の比較だけで n₀ を判断せず、**実データで感度分析（FR-4.7）を行って決める**

#### 構造的ノイズの除去は「辺の存在」側で行う

重みを小さくしても辺は残る。そこで**重みではなく累積値で辺の存在を決める**。

```
辺 (i,j) を張る条件:  Σ w(i,j) ≥ min_edge_weight     （既定 0.3）
```

- 「人数で切る」のではなく「**関係の証拠が十分あるか**で切る」
- 10名定例に数回同席しただけ（0.059 × 3 = 0.18 < 0.3）→ 辺を張らない
- 1on1 が1回でもあれば（1.0 ≥ 0.3）→ 辺を張る
- **これが本来やりたかったこと。** 参加人数は重みの問題、ノイズは証拠量の問題として分離される

#### ハード上限は計算量対策としてのみ残す

- `max_attendees_hard`（既定 50）を超える会議は**ペア展開をスキップ**する
- これは分析上の判断ではなく、n=200 の会議で 19,900 ペアを生成する無駄を避けるためだけのもの
- 関数上すでにほぼゼロなので、**結果に影響しない**（除外件数は `doctor` が報告）

### 5.3 interactions への変換

1イベント = 1行。ペアへの展開はエッジビルダー（§6）で行う。

```csv
event_id,ts,source,channel_type,actor_id,target_ids,group_id,participant_count,duration_min
gcal_a1b2,2026-01-06T10:00:00Z,calendar,meeting,u_001,u_002|u_007|u_015,ical_8831,4,60
```

- `actor_id` / `target_ids` はスキーマとして保持するが、**指標の計算には使わない**
  （主催の記録が信頼できないため。§7.1 を参照）
- `participant_count` = 主催者を含む人数

## 6. グラフ構築

### 6.1 作るグラフ

| グラフ | 用途 | 構築方法 |
|---|---|---|
| **無向グラフ G** | ❶❷❸❹❺❻ | 同席した全ペアに辺を張る |
| **有向グラフ D** | ❷影響力 | 主催者 → 各参加者 |

### 6.2 重み付け

1つの会議（参加者 n 名、所要 d 分、t 日前）から各ペアに与える重み:

```
w = w_size(n) × w_dur(d) × w_resp(r) × w_time(t)

  w_size(n) = σ(n) / (n-1),  σ(n) = 1/(1+exp((n-n₀)/k))    §5.2。既定 n₀=10, k=3
  w_dur(d)  = (d / 60) ^ β                                  β 既定 0.5（逓減）
  w_resp(r) = accepted 1.0 / tentative 0.6 / needsAction 0.8   既定
  w_time(t) = 0.5 ^ (t / half_life)                         half_life 既定 60日
```

#### w_dur — 所要時間も連続変数で

| 所要 | β=0.5 | 考え方 |
|---|---|---|
| 15分 | 0.50 | 立ち話・確認 |
| 30分 | 0.71 | 標準的な1on1 |
| 60分 | 1.00 | 基準 |
| 90分 | 1.22 | |
| 120分 | 1.41 | 2時間は30分の2倍ではなく約2倍（逓減） |

- β=0 で時間を無視（回数ベース）、β=1 で線形。**既定 0.5** は「長時間ほど関係は強いが比例はしない」という逓減を表す
- **人数と時間は独立に効く**: 5名×2時間のワークショップ（0.225 × 1.41 = 0.317）は、5名×30分の定例（0.225 × 0.71 = 0.160）の約2倍

#### w_resp — 返答状況

- `declined` は R3 で既に除外済み
- `needsAction`（未返答）を 0.8 とするのは、**日本の実務では返答しないまま出席することが多い**ため。
  0 にすると欠落が大きくなりすぎる（D3）

#### 累積の仕方

- 同じペアの複数会議は**加算**する（既定）。週次1on1 13回 = 13.0
- オプション: `tie_transform: sqrt | log` で逓減させられる
  - 線形だと、週次1on1の相手がエゴネットワークの重みを独占し、**❶制約スコアが過度に低く（＝ブローカー的に）出る**懸念がある
  - v0.1 は線形を既定とし、**感度分析（FR-4.7）で影響を測ってから既定を決める**

### 6.3 辺の存在判定（構造的ノイズの除去）

**回数ではなく累積重みで判定する**（§5.2）。

```
辺 (i,j) を張る条件:  Σ w(i,j) ≥ min_edge_weight     （既定 0.3）
```

| ケース | 累積重み | 辺 |
|---|---|---|
| 1on1 が1回 | 1.00 | ✅ 張る |
| 5名会議に2回 | 0.45 | ✅ 張る |
| 10名定例に3回 | 0.18 | ❌ 張らない |
| 20名説明会に10回 | 0.019 | ❌ 張らない |

- 「何人の会議か」ではなく「**関係の証拠が十分か**」で切る
- `min_edge_weight` は感度分析の主要パラメータ。0.2〜0.5 で結論がどう変わるかを `relana sensitivity` で提示する

## 7. 指標計算

| 特徴 | 使うグラフ | アルゴリズム | 備考 |
|---|---|---|---|
| ❶ 発想力 | G | Burt's constraint、effective size | 低いほどブローカー |
| ❷ 影響力 | G | **重み付き媒介中心性** | 直接会った相手の数と並べ、**直接の相手が少ないのに、情報の通り道になっている人**を出す |
| ❸❹ 効率性/イノベーション | G | チーム内密度 × 外部範囲（非重複度） | `team` 列でグルーピング |
| ❺ サイロ | G | I/E 比（閾値5.0）＋ **人数で補正した「ランダムの何倍か」**、モジュラリティQ | `dept` 列でグルーピング |
| ❻ 脆弱性 | G | 媒介中心性、関節点、ノード除去シミュレーション、外部単一接点 | 外部ドメインをノードとして含める |

- 100名規模では全指標が数秒（requirements.md §10.1）
- networkx を既定とし、igraph はオプション

### 7.1 カレンダー特有の解釈注記（`caveats` に自動付与）

- 「会議の同席のみに基づく。チャット・メールでの日常的なやり取りは反映されていない」
- 「リモート中心の組織では会議データの比重が高く、対面の立ち話等は捉えられない」
- 「参加者非表示の予定（件数を明記）は分析に含まれていない」
- ❷影響力: 「部門が会議でつながっていない場合、その先には届かないと数える」

### 7.2 会議タイプの推定 — タイトルを取らずに文脈を得る

会議タイトルは取得しない（FR-1.5）。しかし **参加人数・所要時間・定期性・時間帯**の4つから、
会議の種類はかなりの精度で推定できる。**これが分析の解像度を大きく上げる。**

| 推定タイプ | 判定条件 | 関係性の意味 |
|---|---|---|
| **1on1（定期）** | n=2 かつ 定期 かつ 25〜60分 | ★**最強のシグナル。** 指導・信頼・実質的なレポートライン |
| 1on1（単発） | n=2 かつ 単発 | 相談・交渉・初回接触 |
| 小グループ作業 | n=3〜6 かつ 60分以上 | 実質的な協働 |
| チーム定例 | n=3〜10 かつ 定期 かつ 30〜60分 | 所属関係 |
| プロジェクト会議 | n=4〜10 かつ 単発 | 一時的な協働 |
| 情報共有・全体会 | n>12 | 関係の証拠として弱い（重みで自動的に小さくなる） |
| 外部ミーティング | 外部ドメイン参加者を含む | 境界連結者のシグナル |

- タイプは `meeting_type` として interactions に付与し、**指標の解釈に使う**
- タイプ別のエッジ構成比を個人・チーム単位で出力する

### 7.3 1on1 サブネットワーク — 最も価値の高い切り口

**n=2 の会議だけで作ったサブグラフ**を独立した分析対象とする。

| 分かること | 内容 |
|---|---|
| **実質的なレポートライン** | 定期1on1 の相手は実質的な指導関係。**組織図と突き合わせると、公式ラインと実態のズレが見える** |
| **孤立者の検出** | 1on1 が1本もない社員。❻脆弱性とは別の「見えていない人」のリスク |
| **メンタリングの偏り** | 特定の人に1on1 が集中していないか（その人の負荷と、組織の依存） |
| **部門をまたぐ1on1** | 公式の指揮系統を越えた信頼関係。❶発想力の裏付けになる |

> 1on1 は**意図的に時間を取った二者関係**であり、偶然の同席とは質が違う。
> 全会議を混ぜたグラフでは埋もれるため、**別グラフとして必ず出す。**

### 7.4 補助指標 — カレンダーから追加で取れるもの

| 指標 | 定義 | 使い道 |
|---|---|---|
| **主催比率** | 主催した会議 ÷ 参加した会議 | 能動性。❷影響力の補助。「主催が多いが影響力スコアが低い」＝事務的な招集役 |
| **外部会議比率** | 外部ドメイン参加会議 ÷ 全会議 | 境界連結者。❻の外部単一接点検出に直結 |
| **会議負荷** | 窓内の総会議時間 | **❻脆弱性の補強指標。** 書籍 p.112 は「彼に仕事が集中してコネクションを維持できなくなれば業務が停滞する」と指摘。**ブリッジ役が過負荷かどうか**は脆弱性の重要な構成要素 |
| **会議の多様性** | 同席相手の部門エントロピー | ❶発想力の補助。情報源の多様性を直接測る |
| **1on1 被提供率** | 自分が受けている1on1 の本数 | 孤立の検出 |

> ⚠️ **会議負荷は「忙しさの監視」に転用しやすい。** 本OSSでは **❻脆弱性の文脈でのみ**出力し、
> 個人の生産性評価には使わない旨を `does_not_mean` に明記する（非ゴール）。

### 7.5 カレンダー起因の偏りと、その扱い

**出力に必ず添える注記。** これを書かないと誤読される。

| 偏り | 内容 | 対処 |
|---|---|---|
| **会議に出ない働き方** | エンジニア・デザイナー等は会議が少なく、**関係が薄いと誤判定されやすい** | 職種別に比較する（FR-5.2）。全社一括でランキングしない |
| **非会議コミュニケーション** | 立ち話・Slack・メールは一切反映されない | `caveats` に明記。チャットを足せば改善する旨を提示 |
| **リモート/出社の差** | リモート中心だと会議として記録されやすく、出社中心だと記録されない | 拠点別の会議密度を `doctor` が報告し、偏りを可視化 |
| **カレンダー文化の差** | 部門によって「予定を入れる習慣」が違う | 部門別の1人あたり会議数を表示。極端な差があれば警告 |
| **参加者非表示の予定** | 取得できない | 件数を品質メタに記録し、レポートに表示 |

```yaml
source:
  type: gcal
  auth: internal_oauth        # internal_oauth | service_account
  persons: ./persons.csv

collect:
  window_days: 90
  exclude_all_day: true
  fetch_titles: false         # 既定で会議タイトルを取得しない

  drop_declined: true           # R3
  min_attendees: 2              # R4
  max_attendees_hard: 50        # 計算量対策のみ。分析上の閾値ではない
  external_domains_as_entity: true   # R2

graph:
  # 参加人数の重み（§5.2）★最も効く設定
  size_decay:
    n0: 10                      # 対話→一方向の相転移点
    k: 3                        # 相転移の滑らかさ
  # 所要時間の重み（§6.2）
  duration_beta: 0.5            # 0=時間無視 / 0.5=逓減 / 1=線形
  # 返答状況の重み
  response_weight:
    accepted: 1.0
    tentative: 0.6
    needsAction: 0.8
  half_life_days: 60
  min_edge_weight: 0.3          # 辺の存在判定（§6.3）
  tie_transform: linear         # linear | sqrt | log

analysis:
  one_on_one_subgraph: true     # §7.3 1on1 サブネットワークを別途出力

analysis:
  privacy_level: L2           # 実名・個人スコア（既定）
  group_by: dept
  team_by: team
  silo_threshold: 5.0

output:
  roles: [hr_admin, manager, self]
```
