# リレーショナル分析 OSS 要件定義（ドラフト v0.3）

- 作成日: 2026-10-07
- ステータス: ドラフト（未決事項は §13 参照）
- 典拠: 書籍の第5章「ピープルアナリティクスで人事戦略が変わる」（リレーショナルアナリティクスの定義と6つの構造的特徴。書籍そのものはリポジトリに含めない）
- **目的: 人事担当者が、簡単にデータを収集し、その場で従業員のリレーション分析を行えること**
- **ターゲット規模: 従業員100名程度まで**（これを超える組織では収集・分析に時間とコストがかかることを明記して提供する。§10.1）
- **前提1: データ収集も本OSSの範囲**（v0.3 での最大の変更点。§7 FR-1）
- **前提2: 利用者は Claude Code / Codex 等のコーディングエージェントを使える**（補助役として。§3 原則1〜6）

---

## 1. 背景

従来のピープルアナリティクスは **個々の社員の属性データ**（特性：不変／状態：可変）に偏っており、成果が出ていない。
デロイト調査では「組織のパフォーマンス向上につながる人材特性を十分に把握できている」企業はわずか9%。

同等以上に重要なのが **社員と社員の「関係」のデータ（リレーショナルデータ）** であり、
社内の社会的ネットワークに現れる **構造的特徴** を測ることで、誰が／どのチームが成果を出すかを予測できる。

材料となる **デジタル排出物**（メール、チャット、カレンダー、タスク割当などのログ）はすでにどの企業にも存在する。
にもかかわらず普及しない理由は2つ:

1. ネットワーク分析が「きれいなノード・エッジ図を描くこと」で終わり、**パフォーマンス予測に結びつく指標**になっていない
2. リレーショナルデータを取得・分析する**情報システムを持っていない**

### 本OSSがこの2つをどう解くか

| 障壁 | 本OSSの解き方 |
|---|---|
| ② システムがない | **データ収集そのものを本OSSが担う。** 主要SaaSへの公式コネクタ、接続ウィザード、権限申請書の自動生成までを本体機能として提供し、**人事担当者が単独で収集を完了できる**状態を作る（§7 FR-1） |
| ① 図で終わる | **指標の出力に解釈ルール・閾値・出典・限界を機械可読で同梱**し、人間向けレポートにもエージェントの説明にも、必ず「この構造が何を予測するか」と打ち手が付いて回るようにする |

> **人事担当者が、自分の手で、その場で分析を完了できること**が本OSSの存在理由である。
> 「データは各社で用意してください」と言った瞬間に、この目的は達成されない。

### 役割分担

| 担い手 | 役割 |
|---|---|
| **本OSS** | 収集 → 正規化 → 名寄せ → グラフ構築 → 指標計算 → スナップショット → 出力。**一気通貫で提供する** |
| **人事担当者（主役）** | ウィザードに従って接続し、分析を実行し、結果を読む |
| **情シス** | 初回の権限付与のみ（OSSが申請書を自動生成して手間を最小化する。FR-1.3） |
| **コーディングエージェント（補助）** | 未対応ソースのアダプタ作成、設定値の提案、トラブル対応、結果の解釈と打ち手の起案 |

> エージェントは**人事担当者を置き換えるのではなく、担当者が詰まった箇所を埋める**位置づけである。
> エージェントなしでも一通り動き、エージェントがあればさらに広い範囲をカバーできる、という二階建てにする。

## 2. プロダクトゴール

> 「社外のユーザーが、手軽に、社内のリレーショナル分析を実施できる」

| ID | ゴール | 成功基準（案） |
|---|---|---|
| **G0** | **人事担当者が単独で完走できる** | **収集から分析結果まで、人事担当者だけで到達できる。** 情シスへの依頼は初回の権限付与1回のみ。エンジニアの常駐を前提としない |
| **G1** | **その場で分析できる** | 接続完了後、**分析の実行から結果表示まで待たされない**（スナップショット済みデータに対しては即時）。初回収集も進捗が見え、中断・再開できる |
| G2 | **データを社外に出さずに完結** | 既定で外部通信は対象SaaSのAPIのみ。分析・保存はローカル／自社インフラ。生データがLLMのコンテキストに入らない経路が既定 |
| G3 | **説明可能性** | 全指標が出典・計算式・解釈の限界に紐づき、レポートにもエージェントの説明にも必ず付いて回る |
| G4 | **アクセス制御** | **匿名化はしない**（個人を特定して測るのが人事の職務）。**社員への開示も動作の前提としない**。防御は「誰が結果を見られるか」のロール制御に集約する（§9 PR-2） |
| G5 | **拡張性** | コネクタ・指標・レポートがプラグインとして追加でき、**未対応ソースはエージェントが埋められる** |
| G6 | **エージェント・ネイティブ（補助として）** | エージェントがリポジトリを読むだけで、未対応ソースの接続・トラブル対応・結果解釈を担える |
| G7 | **規模の正直さ** | 対応規模（100名まで）を README・CLI・レポートに明示し、超過時は所要時間とコストを事前に警告する |

### 「手軽さ」の具体的な目標

| 区間 | 目標 |
|---|---|
| インストール → 接続ウィザード完了 | 15分（情シスの権限付与待ちを除く） |
| 情シスへの依頼 | **申請書を自動生成**し、担当者が書類を書く時間をゼロにする |
| 初回データ収集 | 進捗表示・中断再開あり。1,000人規模で数時間を許容（バックグラウンド実行） |
| 収集完了 → 初回レポート | **5分以内** |
| 2回目以降の分析（設定変更・別の切り口） | **即時**（スナップショット済みのため） |

### 非ゴール

- 従業員の**監視・勤怠管理・生産性スコアリング**ツールとしての利用（設計上も抑止する）
- メール/チャットの**本文内容の常時解析**（最深レベルの分析はオプトインの別パッケージ。§9参照）
- 個人の**人事評価点の自動算出**
- 指標計算そのものをLLMに行わせること（§3 の設計原則で明確に禁ずる）
- SaaS としてのホスティング提供（v1 時点では）。※ **データ収集機能は提供する**。提供しないのは「他社のデータを預かるクラウドサービス」である
- **大規模組織（目安1,000名超）への最適化**。動作はするが検証対象外とし、時間とコストがかかることを明記する（§10.1）

## 3. 設計原則

本OSSの設計を貫く8原則。以降の機能要件はすべてこれに従う。
**原則0が最上位**で、他のすべての原則は原則0と衝突する場合に譲る。
原則1〜6はエージェント（補助役）に関するもの、原則7は分析の単位に関するもの。

### 原則0: 人事担当者が単独で完走できること（最優先）

他のすべての原則は、この原則と衝突する場合に譲る。

- **専門知識を前提としない。** コードを書かず、SQLを書かず、ネットワーク分析の用語を知らなくても完走できる
- **他部署への依頼は最小化する。** 情シスへの依頼は初回の権限付与1回のみ。その依頼すら申請書を自動生成する（FR-1.3）
- **待たせない。** 収集は進捗が見えて中断・再開でき、収集済みデータに対する分析の切り口変更は即時（原則7のスナップショットがこれを支える）
- **専門用語には必ず説明を添える。** 「制約スコア」「モジュール性」をそのまま画面に出さない

> エージェント（原則1〜6）は、この原則を**補強**するために存在する。置き換えるためではない。

### 原則1: 決定論的コアと非決定論的周辺を厳密に分ける

| 層 | 担当 | 理由 |
|---|---|---|
| **決定論的コア**（OSS本体が提供・テスト済み） | グラフ構築、6指標の計算、プライバシーフィルタ、集計 | **数値が毎回変わってはならない。** LLMに計算させると再現性・監査可能性が失われ、人事意思決定の根拠にできない |
| **非決定論的周辺**（エージェントがその場で担当） | データ探索、アダプタ実装、設定値の提案、結果の解釈文、打ち手の立案 | 各社固有で事前に書けない部分。ここは**出力を検証できる形**にしてエージェントに委ねる |

> **アンチゴール**: 「LLMがネットワーク指標を推定する」機能は作らない。コアは純粋な計算である。

### 原則2: スキーマ・ファースト — 契約は1つだけ

- エージェントが満たすべき契約は **`interactions` スキーマ（§8）1つ**に集約する
- 「このCSVを作れば残りは全部動く」という状態にすることで、エージェントのタスクを**単純な変換問題**に落とす
- スキーマはJSON Schema / Pydantic として機械可読に提供し、ドキュメントの散文に埋もれさせない

### 原則3: 自己修復可能なエラーメッセージ

エージェントは失敗から回復できるが、**失敗の内容が具体的である場合に限る**。

- 全エラーに `error_code` / **何が期待値で何が来たか** / **次に何をすべきか** / 該当行番号を含める
- 例: `E_SCHEMA_MISSING_COLUMN: 'actor_id' が見つかりません。検出された列: [from_user, to_user, ts]。'from_user' を 'actor_id' にリネームしてください`
- `relana validate` は**全エラーをまとめて返す**（1件ずつ直させて往復を増やさない）

### 原則4: 機械可読 I/O を一級市民にする

- すべてのCLIが `--json` を持ち、**人間向け整形出力と機械可読出力を分離**
- 分析結果JSONには数値だけでなく **解釈メタデータ**（閾値、方向、出典ページ、解釈の限界）を同梱する
  → これが「きれいな図で終わる」問題のエージェント時代の解法。エージェントは数値を見て**正しく**語れる

### 原則5: 生データをLLMのコンテキストに入れずに作業できる経路を用意する

エージェント前提にすると**新しいリスク**が生まれる。これを設計で潰す。

| リスク | 対策 |
|---|---|
| 生データ（社員の実名・チャット本文）がLLMプロバイダに送信される | `relana profile` が**実データを出さずに**構造情報だけ返す（列名、型、カーディナリティ、サンプル形状、匿名化済み例示値）。アダプタ開発はこれだけで可能 |
| **プロンプトインジェクション**: 社内チャット本文中の「以前の指示を無視せよ」等をエージェントが読んでしまう | **本文を既定でスキーマに含めない**設計がそのまま防御になる。本文を扱うL3では隔離処理を必須とする |
| エージェントが誤って個人名入りの結果を外部に出す | 出力はロール別に別ファイル生成（PR-2.2）。個人名を含む出力は持ち出し時に警告（PR-2.6） |

### 原則5の帰結: エージェント向けの安全既定

- OSS同梱のエージェント指示書に「**生データファイルを `cat` で全文読まない。`relana profile` を使う**」を明記する

### 原則6: 検証可能性でエージェントの成果物を担保する

エージェントが書いたアダプタが正しい保証はない。**正しさを機械的に確認する手段**を提供する。

- `relana validate` — スキーマ適合、値域、時刻整合、ID参照整合
- `relana doctor` — 名寄せ漏れ、ボット混入、被覆率、極端な外れ値、期間の穴を検出
- **ゴールデンテスト**: アダプタのサンプル入力→期待出力のペアを同梱し、新規アダプタも同じ形式でテストを書かせる

### 原則7: スナップショットを分析の単位にする

分析結果は「いまのグラフ」ではなく、**不変 (immutable) で再現可能なスナップショット**として生成・保存する。
ライブに動くグラフを都度参照するのではなく、**期間を切って固めたものを比較する**のが本OSSの基本動作である。

| 得られるもの | 内容 |
|---|---|
| **データ最小化** | 生データ（通信ログ原本）は短期保持し、**集計済みのスナップショットだけを長期保存**できる。PR-4.3 の保持期間設計が初めて成立する |
| **再現性・監査** | 設定ハッシュ・コードバージョン・データ期間・被覆率をスナップショットに封入。「この人事判断は、いつの、どの設定の分析に基づくか」を後から辿れる |
| **性能** | 毎回全期間を再計算しない。過去分は確定済みとして扱える（NFR-3） |
| **「関係は動的」への対応が基本設計になる** | 時系列比較が後付け機能ではなく、最初から一級の操作になる |
| **エージェントの参照単位** | `snapshot_id` という安定した識別子を指して「前四半期と比べて」と依頼できる。会話をまたいでも指示対象がぶれない |

> **スナップショットは追記のみ。** 再生成は上書きではなく新IDとする（過去の意思決定の根拠を消さないため）。

## 4. スコープ

### In Scope（v1）

- **データ収集**（公式コネクタ、接続ウィザード、権限申請書生成、差分収集、中断再開）★本OSSの中核
- **共通スキーマ・バリデータ・プロファイラ**（未対応ソースをエージェントが埋めるための足場）
- アダプタ作成テンプレート
- 同一人物の名寄せ（identity resolution）
- 重み付き・時間窓付きのネットワーク構築
- **スナップショット生成・保存・比較**（分析の単位。原則7／FR-6）
- **6つの構造的特徴**の算出（§6）
- 出力: 機械可読JSON（解釈メタデータ付き）／静的HTMLレポート／CSV
- アクセス制御（ロール別出力、分析レベル、監査ログ）と透明性（開示・同意テンプレート）
- 社員本人への**データ還元レポート**生成
- **エージェント指示書**（`AGENTS.md` / Claude Code skill）とレシピ集

### Out of Scope（v1）

- 業績データとの統計的因果推論（相関の提示までに留める）
- リアルタイムストリーミング処理
- 多テナント・課金・SSO 等のSaaS基盤
- ~~ベンダー側が管理するOAuthアプリの提供~~ → **撤回。公開OAuthクライアント（PKCE）を同梱する**（FR-1.18）。
  ローカル完結のため、OSS提供者はトークンもデータも一切受け取らない。アプリ登録を各社に強いるのは「気軽さ」と両立しない

## 5. 想定ユーザーとユースケース

### ペルソナ

| ID | ペルソナ | 位置づけ | 期待すること |
|---|---|---|---|
| **P1** | **人事・HRBP・ピープルアナリティクス担当** | **一次利用者（主役）** | 自分の手で接続し、その場で分析し、結果を読めること。コードを書かずに完走できること |
| P2 | 情報システム／セキュリティ | **初回だけ登場** | 権限付与の可否を判断できる材料（申請書・取得項目・保存先）が揃っていること |
| P3 | 事業部マネジャー | 結果の消費者 | 自チームの診断と打ち手を受け取る |
| P4 | 社員本人 | 還元対象 | 自分のネットワークと部門平均の比較。何が収集されているかを知れること |
| **P0** | **コーディングエージェント** | **補助役** | 未対応ソースのアダプタ作成、設定値の提案、トラブル対応、結果の解釈と打ち手の起案 |
| P5 | OSSコントリビュータ／研究者 | 拡張者 | 指標の再現性、独自コネクタ・指標の追加 |

> **P1 が主役。** エージェント（P0）がいなくても一通り動き、いればカバー範囲が広がる二階建てにする。
> P2 を「初回だけ登場」に抑えられるかが導入成否を分けるため、FR-1.3（権限申請書の自動生成）を最優先要件とする。

### 主要ユースケース

| UC | 名称 | 対象 | 問い |
|---|---|---|---|
| **UC-0** | **データ収集のセットアップ** | — | **自社のSlack/メール等を、人事担当者だけで繋ぐには** |
| UC-0b | 未対応ソースの接続 | — | 公式コネクタがないデータを取り込むには（エージェントの出番） |
| UC-1 | アイデア創出人材の発見 | 個人 | よいアイデアを思いつくのは誰か |
| UC-2 | 変革推進のキーパーソン選定 | 個人 | 他者の行動を実際に変えられるのは誰か |
| UC-3 | 納期遵守型チームの編成 | チーム | スケジュール通りに完了できるチーム構成は |
| UC-4 | イノベーションチームの編成 | チーム | 有効なイノベーションを生めるチーム構成は |
| UC-5 | サイロ診断 | 組織 | どの部門がタコつぼ化しているか |
| UC-6 | 組織脆弱性診断・後継者計画 | 組織 | 失ってはならないのは誰か。代替者はいるか |
| UC-7 | 定点観測 | 全体 | 施策の前後でネットワークはどう変わったか |
| UC-8 | 本人へのフィードバック | 個人 | 自分のネットワークは閉じていないか |

### UC-0 の想定フロー（主経路：人事担当者が単独で行う）

```
Day 0  relana init                      → 対話で組織名・期間・プライバシーレベルを設定
       relana permissions --for slack   → 情シスに出す申請書が生成される（担当者は書かない）
         └→ 情シスへ提出（ここだけ他部署に依頼）

       ※ 承認待ちの間に先に試せる経路:
       Slack管理コンソールでエクスポート → relana collect --from ./export
         └→ 当日中に初回レポートが見られる

Day 1  relana connect slack             → ブラウザでOAuth認可。接続テストで対象人数と件数を表示
       relana collect --dry-run         → 「約128万件・推定42分」と事前提示
       relana collect                   → 進捗表示つき。中断・再開可。本文はディスクに書かれない
       relana doctor                    → ボット混入・名寄せ漏れ・被覆率を警告＋修正手順

       relana snapshot create 2026Q1    → 窓90日・コホート確定でスナップショット生成
       relana report                    → HTMLレポートが開く  ← ここまで担当者が単独で到達

以降   relana analyze --features silo --group-by location  → 切り口を変えても即時（再収集なし）
```

### UC-0b の想定フロー（補助経路：エージェントが埋める）

```
人事担当者: 「Backlogのデータも入れたい。公式コネクタがないみたい」
  ↓
エージェント: relana profile ./backlog_export  → 構造だけ把握（生データは読まない）
エージェント: adapters/ のテンプレートから変換スクリプトを書く
エージェント: relana validate → エラーがあれば自己修復 → relana collect --from ./out
エージェント: 結果JSONの解釈メタデータを引用して日本語で説明＋打ち手を提案
```

## 6. 分析要件：6つの構造的特徴

本OSSの中核。**決定論的コアが担当する領域**（原則1）。すべての指標は「構造的特徴 → 予測したいパフォーマンス」の対応を持つ。
（本節の要件IDは `MT-n`。§7 の機能要件 `FR-n` と区別する）

| # | 特徴 | 粒度 | 予測対象 | 中核指標 | 方向 |
|---|---|---|---|---|---|
| ❶ | **発想力** (Ideation) | 個人 | よいアイデアを思いつく社員 | 制約 (Burt's constraint) | **低い**ほど良い |
| ❷ | **影響力** (Influence) | 個人 | 他者の行動を変えられる社員 | 集合的傑出性 (aggregate prominence) | 高いほど良い |
| ❸ | **効率性** (Efficiency) | チーム | 納期を守れるチーム | 内部密度 ＋ 外部範囲 | 内部密度**高** × 外部範囲**広** |
| ❹ | **イノベーション** (Innovation) | チーム | 有効なイノベーションを生むチーム | 内部密度 ＋ 外部範囲 | 内部密度**低** × 外部範囲**広** |
| ❺ | **サイロ** (Silo) | 組織 | 組織のタコつぼ化 | モジュール性（内部/外部比） | 比率 **5:1 超で警戒** |
| ❻ | **脆弱性** (Vulnerability) | 組織 | 失ってはならない社員 | ノードの代替可能性／堅牢性 | 代替不能なノードを検出 |

### 全指標に共通の出力要件（原則4）

各指標の結果JSONは、数値に加えて**解釈メタデータ**を必ず持つ。

```json
{
  "metric": "constraint",
  "feature": "ideation",
  "level": "person",
  "value": 0.31,
  "percentile_in_dept": 12,
  "direction": "lower_is_better",
  "threshold": null,
  "source": "Burt (1992) / 第5章 p.100-102",
  "interprets_as": "斬新な情報へのアクセス可能性",
  "does_not_mean": "創造性そのものの保証ではない",
  "caveats": ["ネットワーク規模に依存するため同規模集団内で比較すること"],
  "suggested_actions": ["制約の低い人材に部門横断の提案機会を与える"]
}
```

> この `interprets_as` / `does_not_mean` / `caveats` が、エージェントによる**過剰解釈を構造的に防ぐ**。

### MT-1 ❶ 発想力 — 制約 (constraint)

- 定義: Burt の構造的空隙理論における constraint
  `C_i = Σ_j ( p_ij + Σ_q p_iq · p_qj )² , q ≠ i, j`
  （`p_ij` = i の全接触量に占める j への接触割合）
- 補助指標: effective size、efficiency、ブローカー役割分類（coordinator / gatekeeper / representative / consultant / liaison）
- 出力: constraint スコアと**部門内パーセンタイル**、複数クラスタを跨ぐ近傍の可視化
- `does_not_mean`: 創造性の保証ではなく「斬新な情報へのアクセス可能性」

### MT-2 ❷ 影響力 — 集合的傑出性 (aggregate prominence)

- 「最も多くの同僚から影響力があると**評価される**人物 ≠ 実際に影響力のある人物」を実装で体現する
- 定義: 自分のコネクション**の先のコネクション**まで織り込んだ再帰的中心性
  → 重み付き無向グラフ上の **媒介中心性**（他の人どうしの最短経路がその人を通る割合）
- 出力:
  - 影響力スコア上位者を**部門ごとに N 人**抽出（書籍事例：9事業部×5名）
  - 次数中心性（人気）と集合的傑出性の**乖離ランキング**（＝見落とされやすい真のインフルエンサー）

### MT-3 ❸ 効率性 / ❹ イノベーション — 内部密度 × 外部範囲

同じ2変数を**逆向きに**使う。この対比を出力で明示することが要件。

| 変数 | 定義（案） |
|---|---|
| **内部密度 (internal density)** | チーム内メンバー間の重み付きエッジ密度。信頼・合意形成の代理指標 |
| **外部範囲 (external range)** | チーム外アルター集合の広さ × **非重複度**（メンバー間で外部接触先が重複していないほど高い） |

- 出力: チームを `内部密度 × 外部範囲` の **2軸4象限**で「効率型／イノベーション型／閉鎖型／拡散型」に判定
- 目的（納期遵守 or イノベーション）を指定すると推奨象限が示される
- チーム編成シミュレーション: メンバー候補の入替による両指標の変化を試算
- `caveats`: 「効率性の特徴を持つチームはイノベーション集団としては失敗しやすい」

### MT-4 ❺ サイロ — モジュール性

- 定義: グループ単位の **I/E 比率** = 内部コミュニケーション量 ÷ 外部コミュニケーション量
- **閾値: 5:1 超で「有害なレベルのサイロ化」と警告**（設定で変更可、`threshold` としてJSONに同梱）
- 補助指標: Newman モジュラリティ Q、部門間コミュニケーション行列
- グルーピング軸は属性（部門・拠点・職種・入社年次）から任意選択
- 出力: 部門別 I/E 比率ランキング（書籍事例: 運営部門 13:1）、断絶ペアと既存ブリッジ人材

### MT-5 ❻ 脆弱性 — ノードの代替可能性

- 定義: ノード除去シミュレーションによる連結性・到達性の毀損度
- 計算要素: 媒介中心性、関節点／ブリッジエッジ、**代替可能性**（繋いでいるペアを他に繋げる人の数）、外部エンティティへの**単一接点**検出
- 出力:
  - 「肩書きは目立たないが情報の流れに不可欠な人物」リスト（**アルビンド検出**）
  - 各リスク人物の**代替候補**提示（後継者育成計画の入力）
  - 離職・休職シナリオ別の堅牢性スコア
- `does_not_mean`: 個人の処遇判断材料ではない。後継者計画・BCPのための指標である

## 7. 機能要件

### FR-1 データ収集 ★本OSSの中核

**データを集めるところまでが本OSSの責務。** 人事担当者が単独で収集を完了できることを要件とする。

#### FR-1.1 収集方式

| 方式 | 対象 | 継続取得 | 人事担当者の負荷 | 情シスの関与 |
|---|---|---|---|---|
| **A. API接続** | Slack, Microsoft 365, Google Workspace, Jira, GitHub ほか | ✅ 自動 | **許可ボタン1回**（FR-1.18） | 経路により不要 |
| **B. エクスポート取込** | 各SaaSの管理コンソールが出す zip / csv | 手動 | ファイルを指定するだけ | 不要な場合が多い |
| **C. 監査ログ** | M365 Unified Audit Log, Google Workspace Reports API | ✅ 自動 | 同上 | 権限が重い（大企業向け） |
| **D. 軽量サーベイ** | デジタル排出物が取得できない組織 | — | 配信と督促 | 不要 |
| **E. エージェント駆動収集** ★既定 | カレンダー | 都度 | **エージェントに頼むだけ** | **不要** |

- **B を「まず試す」経路として重視する。** 権限申請を待たずに当日中に結果が見られる導線が、導入の成否を分ける
- **D について**: 書籍はサーベイを「コストが高く偏りも大きい」と明確に否定している（1.5万人×30分＝100万ドル相当）。
  本OSSでも**本線はAPI接続**とするが、Slack等を導入していない組織が最初の一歩を踏み出すための**5分で終わる最小サーベイ**を用意する。
  サーベイ由来のスナップショットには `data_origin: survey` を記録し、**デジタル排出物由来のものと混ぜて比較しない**
- **E について**: §7.1a。**エージェントのカレンダー連携で読み、`relana ingest` で取り込む**。
  利用者に Google Cloud プロジェクトを作らせないため、これを既定の主経路とする

#### §7.1a 方式E: エージェント駆動収集 ★既定の主経路

> 「コーディングエージェントを使って簡単にデータが取れる必要がある」への回答。

**v0.6 での訂正**: 当初、エージェントのカレンダー連携（E-2）を「取得範囲がその人の見える範囲に
限られる」という理由で主経路から除外していた。**これは誤りだった。**
エージェントの連携は利用者自身の権限で動くため、**到達範囲は内部OAuthクライアント方式（方式1）と同一**である。
社内のカレンダー共有が有効なら、同僚の予定を参加者つきで読める。
範囲の制約は方式1と同じであり、E-2 を避ける理由にはならない。

したがって **E-2 を既定の主経路とする。** 利用者に Google Cloud プロジェクトを作らせないため。

| | **E-2: エージェントの連携で読む** ★既定 | **E-1: エージェントが収集スクリプトを書く** |
|---|---|---|
| 利用者の準備 | **何もない** | GCPプロジェクト＋OAuthクライアントの作成 |
| 到達範囲 | 社内共有が有効なら全社 | 同じ |
| データ量 | **文脈の管理が必要**（下記） | 制限なし |
| 継続運用 | 都度エージェントが実行 | cron で自動化できる |
| 向く場面 | **初回・試用・100名規模** | 継続運用・大規模 |

##### E-2 を成立させる設計

唯一の実質的な制約は**データ量**である。これを3つで解く。

| 課題 | 解き方 |
|---|---|
| 全員分を読むと量が多すぎる | **全員分を読む必要がない。** 1人分を読むとその人の会議の全参加者どうしの関係が得られるため、100名なら15〜20名分で足りる（FR-1.18.3b） |
| 読んだ予定が文脈に残り続ける | **1人読んだら即座に `relana ingest` して捨てる。** まとめて渡さない |
| どこまで読めば足りるか分からない | `relana next-calendars` が出現回数の多い未読の人を提案し、`relana doctor` の被覆率で打ち切りを判断する |

- **FR-1.19 `relana ingest`** — エージェントは1行1件の最小形 JSONL を書くだけでよい。
  重複排除（R8）・会議室の除去（R1）・会議種別の推定は relana が受け持つ
- **FR-1.20 `relana next-calendars`** — 次に読むと効率がよいカレンダーを提案する
- **FR-1.21 社内ドメインの推定** — 名簿が無いため、どこまでが社内かもデータから決める。
  ただし件数だけで複数ドメインを言い当てるのは信用できないため、**最頻の1つのみを社内とし、
  紛らわしいものは確認を促す**
- 手順はスキル `.claude/skills/calendar-collect/SKILL.md` に記述する

##### 残る論点: LLM を経由すること

E-2 では会議のメタデータがエージェントの文脈を通る。これは事実であり、設計で消せない。

- 通るのは**メタデータのみ**（誰と誰が・いつ・何分）。本文・場所・添付は書き出さない
- 1on1 と単発会議のタイトルも書き出さない（定期グループ会議のタイトルのみ）
- 利用者の判断材料として、この点は `docs/governance/` に記載する

継続運用の段階で気になる場合は、E-1（スクリプト方式）に移行すればデータは LLM を通らなくなる。
**初回は E-2 で始め、必要になったら E-1 に移る**のが現実的な段取りである。

#### FR-1.2 接続ウィザード `relana connect <source>`

- 対話形式で、必要な情報を1つずつ聞く。専門用語には必ず説明を添える
- ブラウザを開いてOAuth認可 → **トークンはローカルに暗号化保存**（OSS提供者のサーバを一切経由しない）
- OAuthアプリは**各社が自社テナントに登録する**方式とし、登録手順をウィザードが画面つきで案内する
- **接続テスト**: 取得できる範囲・対象人数・推定イベント数をその場で表示
- 失敗時は原因と次の手順を日本語で返す（権限不足ならどのスコープが足りないかを名指しする。原則3）

#### FR-1.3 権限申請書の自動生成 `relana permissions --for <source>` ★導入障壁の本丸

人事担当者が単独で越えられない唯一の壁が **情シス・セキュリティ部門の承認**。ここを機能で潰す。

- 必要なスコープ一覧と、**それぞれが何のために必要か**の説明
- **取得しないもの**（本文・件名・添付・ファイル内容）の明示
- データの保存先・保持期間・誰がアクセスできるかの記載
- そのまま回覧できる申請書（Markdown / PDF）を出力
- セキュリティレビュー向けのQ&A雛形を同梱

#### FR-1.4 最小権限

- **読み取り専用スコープのみ**を要求する。書き込み・送信・削除の権限は一切要求しない
- 本文を読まずに済むAPI・フィールドを優先的に選択する（例: 会話一覧APIでメタデータのみ取得）

#### FR-1.5 収集時点での本文破棄 ★

- **本文はディスクに書かない。** API応答から必要なメタデータだけを抽出し、本文はメモリ上で破棄する
- 収集ログ・エラーログにも本文を残さない
- → 情報漏洩リスクを**収集段階で断つ**。§9 PR-4 の収集最小化を、設定ではなく実装で担保する

#### FR-1.6 見積もりとドライラン

- `relana collect --dry-run` → 対象期間、対象人数、推定イベント数、推定所要時間、API呼び出し回数
- 人事担当者が「どれくらいかかるか」を実行前に把握でき、情シスにも事前説明できる

#### FR-1.7 中断・再開・レート制限

- 大規模組織では初回収集に数時間かかる。**チェックポイントを保存し、中断・再開できる**こと
- API のレート制限を尊重し自動バックオフ。進捗と残り時間を表示
- バックグラウンド実行に対応（収集中も他の作業ができる）

#### FR-1.8 差分収集

- 前回取得以降のみを取得。べき等性を担保（同じ期間を再取得しても重複イベントが増えない）
- 定期実行（FR-6.8）と組み合わせてスナップショットを自動生成

#### FR-1.9 収集スコープの制御 — プライバシーの最前線

| 対象 | 既定 | 理由 |
|---|---|---|
| パブリックチャンネル | **ON** | 最も機微性が低く、組織構造をよく反映する |
| プライベートチャンネル | **OFF** | 明示的な選択を要する |
| **DM / 個人間メール** | **OFF** | 最も機微。ONにする場合は社員への追加説明と同意を必須とする |
| 外部ドメインとのやり取り | ON（外部エンティティとして集計） | ❻脆弱性の単一接点検出に必要 |

- 対象期間・対象部門・対象チャネルを収集前に絞り込める
- **収集範囲の設定内容が、社員向け開示文書（PR-3.3）に自動で反映される**こと

#### FR-1.10 未対応ソースへの対応（エージェントの出番）

- `relana profile <path>` — 入力の**構造情報のみ**を返す（列名・型・カーディナリティ・欠損率・ネスト構造・時刻列候補）。
  **実データ値は出さない**（原則5）。エージェントはこれだけ見てアダプタを書ける
- アダプタテンプレート（変換の雛形、型注釈、TODO、テストの空枠）
- 生成されたアダプタをコミュニティが**公式化できる昇格導線**を用意する

#### 対応ソースと取得内容

| 種別 | ソース | 取得するもの（メタデータのみ） | 方式 |
|---|---|---|---|
| チャット | **Slack** | DM/チャンネル投稿、スレッド返信、メンション、リアクション | A / B |
| チャット | Microsoft Teams | 同上 | A / C |
| メール | Google Workspace | 送受信ログ（To/Cc/Bcc の別）。**本文・件名は取得しない** | A / C |
| メール | Microsoft 365 | 同上 | A / C |
| カレンダー | Google Calendar, Outlook | 同席関係、会議サイズ、所要時間。**タイトル・議題は取得しない** | A |
| タスク | Jira, Backlog, Asana, Trello | 担当者割当、コメント関係、レビュー関係 | A |
| 開発 | GitHub / GitLab | PRレビュー、コメント、共同編集 | A |
| 調査 | 軽量サーベイ | 自己申告のネットワーク（fallback） | D |
| 汎用 | **CSV / JSONL** | 誰が・いつ・誰に・どの種類の接点を持ったか | B |
| 属性 | 人事マスタCSV | 部門・役職・拠点・入社日（グルーピングと統制変数） | B |

### FR-2 検証（バリデータ／ドクター）

原則3・6の実体。**エージェントの自己修復を可能にする最重要機能。**

- **FR-2.1 `relana validate`** — スキーマ適合、必須列、型、値域、時刻整合、ID参照整合
  - **全エラーを一括で返す**。各エラーに `error_code` / 期待値 / 実測値 / 該当行 / **修正手順**
  - 終了コードで成否を返し、エージェントが分岐できること
- **FR-2.2 `relana doctor`** — データ品質の警告
  - 名寄せ未解決ID、ボット／共有アカウントの疑い、外部ドメイン比率
  - **被覆率**（在籍者のうち何%がイベントに登場するか）
  - 期間の穴、極端な外れ値（全社通知チャネル等）、重複イベント
  - 各警告に**推奨アクション**を添える
- **FR-2.3** ゴールデンテスト — サンプル入力と期待出力のペアを同梱。新規アダプタも同形式で追加させる

### FR-3 名寄せ（identity resolution）

- **FR-3.1** メールアドレス / Slack ID / GitHub アカウント等を**1人の person_id** に統合
- **FR-3.2** 人事マスタCSVによるマッピング指定、および**自動マッチ候補の提示**（確信度付き。採否はエージェント／人間が決める）
- **FR-3.3** ボット・共有アカウント・外部ドメインの除外／外部扱いルールを設定可能
- **FR-3.4** 未解決ID一覧を必ず出力（`doctor` と連動）

### FR-4 ネットワーク構築（エッジビルダー）

書籍の「**すべての行動を同等に扱えるわけではない**（『いいね』とCcメールは同じではない）」への対応。

- **FR-4.1** **チャネル別の重み**を設定ファイルで定義（例: DM 1.0 / メンション 0.6 / 同一会議 0.3 / リアクション 0.1）
  - 既定値を提供しつつ、**その既定値の根拠をコメントで明示**（エージェントが調整の可否を判断できるように）
- **FR-4.2** 方向性の扱いを選択可能（有向／無向／相互性による重み補正）
- **FR-4.3** 時間減衰（半減期指定）と分析時間窓（例: 直近90日）
- **FR-4.4** **会議・大規模チャネルの正規化**: 参加者 n 人のイベントは `1/(n-1)` 等で正規化
- **FR-4.5** ノイズ除去: 最小相互作用回数の閾値、全社通知チャネルの除外
- **FR-4.6** 期間除外（例: 育児休暇中の数カ月をデータから除外）
- **FR-4.7** **感度分析** `relana sensitivity` — 重み設定を振った際に結論（上位者・サイロ判定）がどれだけ変わるかを返す
  → エージェントが「この結論は設定依存か、頑健か」を言えるようにする

### FR-5 指標計算

§6 の通り。加えて:

- **FR-5.1** すべての指標に**生値・z値・部門内パーセンタイル**を付与
- **FR-5.2** 規模依存指標は規模補正、または比較可能な集団内でのみランキング
- **FR-5.3** 属性データ（部門・勤続年数など）を統制変数として並記し、属性分析との補完関係を示す
- **FR-5.4** 計算の**再現性**: 乱数シード固定、バージョンと設定ハッシュを結果に埋め込む

### FR-6 スナップショット（分析の単位）

書籍の「**一度きりの分析では意味がない。関係は動的**」への対応であり、**原則7の実体**。
本OSSの全分析はスナップショットに対して行われ、単発の実行もまた1個のスナップショットを生む。

#### FR-6.1 スナップショットの定義

スナップショット = **ある時間窓のイベントから構築した `edges` + `metrics` + 品質メタ + 再現情報の、不変な一式**。

| 構成要素 | 内容 |
|---|---|
| `snapshot_id` | 一意かつ可読な安定ID（例: `2026Q1__w90d__cfg-a1b2c3`） |
| **窓定義** | 開始・終了、窓長、窓タイプ（FR-6.2） |
| **母集団定義** | 対象者の決め方（在籍者／同意済みのみ／コホート固定） |
| **再現情報** | 設定ハッシュ、コードバージョン、入力データのフィンガープリント |
| **品質メタ** | 被覆率、イベント数、ソース構成比、適用した除外ルール |
| **成果物** | `edges`、`metrics`（6特徴すべて）、グループ定義 |

#### FR-6.2 窓の種類 — 用途で使い分けられること

| 種類 | 説明 | 主な用途 |
|---|---|---|
| **固定窓** (tumbling) | 四半期ごとなど、重なりなしで区切る | 定点観測・期間比較 |
| **移動窓** (rolling) | 直近90日を毎月など、重なりあり | トレンドの平滑化、短期ノイズの除去 |
| **任意区間** (ad hoc) | 施策の前後など自由に指定 | 介入効果の確認 |

- 窓長の既定値は指標ごとに異なりうる（関係の成立に必要な観測期間が違うため）。既定値とその根拠を明示すること

#### FR-6.3 比較可能性の検証 ★本機能群の最重要要件

**スナップショット同士は無条件には比較できない。** 差分を出す前に互換性を検証する。

| 非互換の原因 | 症状 | 対処 |
|---|---|---|
| **窓長が違う** | 相互作用の総量が違い、密度系の指標が動く | 窓長一致を必須化、または強度を期間正規化 |
| **母集団が違う**（入退社） | ネットワーク規模が変わり constraint・中心性が動く | **コホート固定モード**（FR-6.5） |
| **データソース構成が変わった** | 新チャネル追加だけでエッジが増える | ソース構成比を比較して警告。共通ソースのみでの再計算を提案 |
| **設定が違う**（重み・閾値） | 数値が実態でなく設定由来で動く | 設定ハッシュ不一致を警告し、再計算を促す |
| **被覆率が違う** | 一部部門のデータ欠損で見かけ上サイロ化 | 被覆率差が閾値超で警告 |
| **コードバージョンが違う** | 指標実装の変更で値が動く | バージョン差を警告。必要なら旧版で再計算 |

→ **`relana diff` は非互換を検出したら黙って差分を出さず、理由と対処手順を返す**（原則3）。
　 これがないと「組織が改善した」のか「データが変わっただけ」なのかを取り違える。

#### FR-6.4 差分・トレンド

- **`relana diff A B`** — スコア変化、新規／消滅エッジ、サイロ化の進行、脆弱人物の増減、象限移動したチーム
- **`relana trend`** — N個のスナップショット系列を時系列で返す
- **変化の有意性**: ノイズと本物の変化を区別する材料を添える（期間内変動の分布における位置、順位変化の安定性、最小検出可能変化量）
  → エージェントが「誤差の範囲です」と言えるようにするための要件

#### FR-6.5 コホート固定（balanced panel）

- 両期間に**在籍かつ同意済み**の人のみに限定して再計算するモード
- 人事判断に用いる比較では**これを既定**とする（人の出入りによる見かけの変化を排除するため）

#### FR-6.6 期間除外との整合

- FR-4.6 の除外（育児休暇など）はスナップショット定義に記録され、差分時に**両スナップショットで自動的に揃えられる**こと

#### FR-6.7 組織変更・M&A をまたぐ比較

- 組織変更でグルーピング定義が変わる場合、**旧軸・新軸のどちらでも再集計できる**こと
- 買収前後のスナップショットを比較し、脆弱性（❻）の変化を可視化

#### FR-6.8 定期実行

- cron / CI でスナップショットを自動生成。**エージェントを常駐させず、決定論的コアだけで回る**こと
- 生成完了時に品質メタ（被覆率低下など）の警告を出す

#### FR-6.9 不変性と系譜

- 生成後のスナップショットは**変更しない**。再計算は新IDで行い、`parent_snapshot_id` を記録して系譜を辿れること
- スナップショットの削除は明示操作のみ（FR-11.7）

### FR-7 出力・レポート

- **FR-7.1 機械可読出力（一級）**: 解釈メタデータ付きJSON。エージェントがこれを読んで説明文を生成する
- **FR-7.2 人間向け出力**: 静的HTMLレポート（単一ファイル、オフライン閲覧可）／CSV
- **FR-7.3** **「きれいな図」で終わらせない** — 全ての図に「この構造が何を予測するか」と打ち手候補を添える。エージェント経路では FR-7.1 の `interprets_as` / `suggested_actions` がこれを担う
- **FR-7.4** マネジャーが自部門だけを見られる**スコープ制限出力**
- **FR-7.5** 日本語／英語の i18n（解釈メタデータも両言語）

### FR-8 社員へのデータ還元（任意機能）

書籍の提言「会社が収集するあらゆるリレーショナルデータを社員に還元すること」への対応。
**本OSSでは任意機能とし、必須要件とはしない**（FR-1.18.5）。

- **FR-8.1** 社員個人向けレポートの一括生成（自分のネットワーク図、制約スコア、**所属部署平均との比較**）
- **FR-8.2** 他者の個人スコアは含めない（本人 + 集計値のみ）
- **FR-8.3** メンタリング／1on1 の対話材料として使える体裁

### FR-9 プライバシー・ガバナンス（§9 に詳述）

### FR-10 設定・再現性

- **FR-10.1** 分析定義は**単一YAML**で完結（重み、窓、閾値、グルーピング、プライバシーレベル）
  - **コメント付きの完全なサンプル設定**を同梱（エージェントがこれを読んで項目の意味を理解できる）
- **FR-10.2** 同じ入力＋同じ設定 → 同じ出力
- **FR-10.3** レポートに設定スナップショット・データ期間・被覆率を必ず埋め込む

## 8. データモデル（共通スキーマ案）

> 原則2により、**これが唯一の契約**。JSON Schema として機械可読に提供する。

### interactions（相互作用イベント）

| カラム | 型 | 必須 | 説明 |
|---|---|---|---|
| `event_id` | string | ✅ | 一意ID |
| `ts` | timestamp | ✅ | 発生時刻（ISO 8601, UTC） |

| `actor_id` | string | ✅ | 起点となる人 |

| `duration_min` | int | | 会議などの所要時間 |
| `weight_hint` | float | | ソース固有の重み材料 |

> 本文・件名・添付は**スキーマに含めない**（既定）。これは原則5のプロンプトインジェクション対策でもある。

### persons（人マスタ）

| カラム | 説明 |
|---|---|
| `person_id` | 内部ID |
| `display_name` | **表示名（既定で実名を表示する）**。疑似ID化は外部共有時のオプション（PR-2.4） |
| `dept` / `team` / `location` / `role` / `grade` | グルーピング・統制変数 |
| `hired_at` / `left_at` | 在籍期間 |
| `is_bot` / `is_external` | 除外・外部扱いフラグ |
| `consent_status` | 同意状況（§9） |

### identities（アカウント対応表）
`person_id` × (`source`, `source_user_id`, `email`)

### snapshots（分析の単位 / 原則7・FR-6）

| カラム | 説明 |
|---|---|
| `snapshot_id` | 一意ID（可読な命名規則を持つ） |
| `parent_snapshot_id` | 再計算元（系譜。FR-6.9） |
| `window_start` / `window_end` / `window_type` | 窓定義（tumbling / rolling / ad_hoc） |
| `population_mode` | active / consented / cohort_fixed |
| `cohort_ref` | コホート固定時の基準スナップショット |
| `config_hash` / `code_version` / `input_fingerprint` | 再現情報 |
| `coverage_rate` / `event_count` / `source_mix` | 品質メタ（比較可能性の判定に使う） |
| `privacy_level` | L1 / L2 / L3 |
| `created_at` / `created_by` | 監査（PR-5.1） |

### edges（構築済みエッジ）
`snapshot_id, src, dst, weight, interaction_count, channels[]`

### metrics（指標結果）
`snapshot_id, level(person/team/org), entity_id, metric_name, value, zscore, percentile` ＋ 解釈メタデータ（§6）

> `edges` / `metrics` は必ず `snapshot_id` に属する。**スナップショットに属さない分析結果は存在しない。**

## 9. プライバシー・ガバナンス要件

書籍の指摘：リレーショナルデータは **受動的に収集される**ため、社員は収集も分析も意識していない可能性がある。
**透明性の確保が企業が最初にすべき仕事**であり、「後回しにすると導入そのものが頓挫する」。
→ **本OSSはプライバシー機能をオプションではなくコア機能として実装する。**

> **前提（v0.4 での方針決定）: 匿名化は行わない。**
> 誰がどのような状態にあるかを把握することは人事の職務であり、匿名化された集計値では
> 「アルビンドは誰か」「誰が真のインフルエンサーか」という本OSSの中心的な問いに答えられない。
> 書籍が価値があるとする分析も、個人を特定する L2 のレベルにある。
>
> したがって本OSSは **「匿名化による保護」ではなく「アクセス制御と透明性による保護」** を設計の軸とする。
> 守り方を変えるのであって、守らないのではない。

### PR-1 分析深度レベル

| レベル | 内容 | 個人特定 | 既定 |
|---|---|---|---|
| **L1: 集計のみ** | 部門単位の集計。個人は出さない | 不可 | 選択可（必要な場合のみ） |
| **L2: 個人スコア** | **誰がどんなネットワークを持つかを実名で明示。** インフルエンサー・脆弱性の特定 | 可 | ✅ **デフォルト** |
| **L3: 内容解析** | 本文・投稿内容をMLで解析し専門性やトピックを特定 | 可 | **別パッケージ＋強い警告**（本文を扱うため別格） |

- レベルは設定ファイルで宣言し、**結果JSONとレポート表紙に常時表示**
- **L1 は「個人を見ない」という選択肢として残す**（全社への結果共有時など、用途によって使い分ける）
- **L3 のみ別格**。本文を扱うため、プロンプトインジェクション隔離を必須とし、既定では同梱しない

### PR-2 アクセス制御 ★匿名化に代わる主たる防御

匿名化を外す以上、**「誰がその結果を見られるか」が唯一かつ主たる防御**になる。ここを曖昧にしない。

- **PR-2.1 ロール定義** — 出力の閲覧範囲をロールで制御する

| ロール | 見えるもの |
|---|---|
| **人事管理者** | 全社・全個人のスコア（フルアクセス） |
| **経営層** | 全社の集計 ＋ 必要に応じて個人スコア（設定で選択） |
| **部門マネジャー** | **自部門のメンバーのみ**（他部門の個人スコアは見えない） |
| **社員本人** | 自分のスコア ＋ 所属部門の平均（FR-8。他者の個人スコアは含まない） |

- **PR-2.2 出力の分離** — ロールごとにレポートを別ファイルとして生成する。
  「1つのレポートを権限で出し分ける」のではなく、**最初から渡してよい内容だけを含むファイルを作る**（誤配布の事故を構造的に防ぐ）
- **PR-2.3 保管と配布の要件** — 個人名入り出力の保存先・暗号化・配布方法をセットアップ時に明示的に設定させる
- **PR-2.4 疑似ID化はオプションとして残す** — 既定OFF。外部共有・研究用途・ベンダー相談などで必要な場合に使う
- **PR-2.5 k匿名（最小集計人数）はオプションとして残す** — 既定OFF。L1で全社共有する場合などに有効化できる
- **PR-2.7 アクセス制御が唯一の統制である旨を実装者向けに明記** — 匿名化も開示も既定で行わないため、ロール別出力（PR-2.2）と保管要件（PR-2.3）の実装品質が本OSSの統制水準そのものになる
- **PR-2.6 持ち出し時の警告** — 個人名を含む出力をエクスポートする際、取り扱い注意の旨をファイル先頭とCLI出力に表示する

### PR-3 開示・同意（すべて任意機能）

**本OSSは開示・同意を動作の前提条件としない**（FR-1.18.5）。以下は必要とする組織のために提供する。

- **PR-3.1** 合意書テンプレート（日本語／英語）を同梱 — **任意**
- **PR-3.2** 同意状況を `persons.consent_status` で管理し、未同意者を分析から除外できる — **機能として提供。既定は全員対象**
- **PR-3.3** 社員向け開示ドキュメントのテンプレート（何を集め、何を集めないか、誰が見るか） — **任意**
- **PR-3.4** 利用目的の公表文テンプレート（プライバシーポリシー・就業規則への記載用） — **任意。開示を行わない運用でも使える最小構成**

### PR-4 収集の最小化

- **PR-4.1** 既定でメタデータのみ（本文・件名・添付を取得しない）
- **PR-4.2** 取得項目をソースごとにホワイトリスト指定
- **PR-4.3** **生データとスナップショットで保持期間を分ける**（原則7の主要な効用）
  - 生データ（`interactions` 原本）: 短期保持 → 期限後に自動削除
  - スナップショット（集計済み・本文を含まない）: 長期保持 → 時系列比較を維持できる
  - 生データ削除後もスナップショットの再現情報は残り、**何に基づく分析かは説明できる**（ただし再計算は不可である旨を記録）

### PR-5 監査・説明責任

- **PR-5.1** 誰がいつどの設定で分析を実行したかの**監査ログ**（エージェント実行も人間実行と同じく記録）
- **PR-5.2** レポートに使用データの期間・被覆率・除外ルールを明記
- **PR-5.3** 用途制限の明示: 「解雇・評価・懲戒の根拠に用いない」旨を結果JSON・レポート・README に記載

### PR-6 法令・労務上の考慮（ドキュメントとして提供）

- 日本: 個人情報保護法（利用目的の特定・通知、第三者提供）、労働者のモニタリングに関する指針、就業規則・労使協議
- EU: GDPR（適法根拠、DPIA、データ主体の権利）
- 米国: 州法（CCPA 等）
- **追加論点（エージェント前提）**: LLMプロバイダへのデータ送信が「第三者提供」に当たるかの整理。
  → **既定の作業経路では生データが送信されないこと**を設計で担保し、その旨をチェックリストに明記する
- → `docs/governance/` に導入チェックリストとして提供（法的助言ではない旨の免責付き）

| NFR-1 | **データ主権** | 既定で外部通信ゼロ。テレメトリなし。エアギャップ環境で動作 |
| NFR-2 | **導入容易性** | 1コマンドでインストール（pip / Docker）。**コードを書けない人事担当者が単独で収集〜レポートまで到達できる**（原則0） |
| NFR-3 | **性能・対応規模** | §10.1 の規模別目安を満たす。**上限を隠さず明示する**（README・`relana doctor`・レポート） |
| NFR-4 | **段階的縮退** | 規模が上限を超えたら黙って遅くならず、**事前に警告し代替手段を提示して停止**する（FR-5.5） |
| NFR-5 | **再現性** | 設定ファイル＋入力ハッシュで結果を再現可能。**LLMを介さず再実行できる** |
| NFR-6 | **テスト** | 各指標に既知グラフでの正解値テスト。アダプタにゴールデンテスト |
| NFR-7 | **拡張性** | アダプタ／指標／レポートがエントリポイント経由で追加可能 |
| NFR-8 | **i18n** | 日本語・英語（CLI、レポート、解釈メタデータ、ドキュメント） |
| NFR-9 | **ライセンス** | Apache-2.0（特許条項ありで企業採用しやすい）を推奨 |
| NFR-10 | **ドキュメント** | 指標ごとに定義・計算式・出典・解釈の限界。**`relana explain` から同内容を機械可読で取得できる** |
| NFR-11 | **セキュリティ** | 認証情報は環境変数/シークレットストア。生データ暗号化オプション |
| NFR-12 | **エージェント適合性** | 未対応ソースの接続をエージェントが**人間の追加介入1回以下**で完了できること |
| NFR-13 | **収集の堅牢性** | API のレート制限・一時障害・トークン失効から**自動回復または明確な指示で復帰**できる。収集の中断で成果がゼロにならない |
| NFR-14 | **収集の安全性** | 本文がディスク・ログ・メモリダンプに残らないこと（FR-1.5）。トークンは暗号化保存し、OSS提供者のサーバを一切経由しない |

### 10.1 対応規模 ★ターゲットは100名規模まで

> **本OSSが公称する対応規模は「従業員100名程度まで」。**
> 50〜100名を快適に扱える範囲とし、**100名を超える組織では収集・分析ともに時間とコストがかかる**ことを明記して提供する。

#### なぜ100名で区切るか

| 理由 | 内容 |
|---|---|
| **「その場で」が本当に成立する** | 100名なら**全6指標が数秒で完了**する（下表）。G1「その場で分析できる」が誇張なく実現する |
| **収集が現実的** | 四半期あたり35〜50万イベント・数十MB。エクスポート取込なら**数分** |
| **検証しきれる** | ベンチマークもプライバシー設計も、1つの規模帯に絞れば実測で裏づけられる |
| **小さく宣言して確実に動かす** | OSSの信頼は「どこまで動くか」を正直に書くことで得られる。大風呂敷を広げて遅いほうが損失が大きい |

#### 100名規模での処理時間（見積もり）

| 指標 | 計算量 | 100名（エッジ約3,000）での演算量 | 見込み |
|---|---|---|---|
| ❷ 影響力（媒介中心性） | O(n·m) | 〜30万 | **数秒** |
| ❺ サイロ（I/E比・モジュラリティ） | O(m) | 〜3千 | **1秒未満** |
| ❸❹ 効率性・イノベーション | チーム単位 | 〜1万 | **1秒未満** |
| ❶ 発想力（Burt's constraint） | O(Σ_i d_i²) | 〜25万 | **1秒未満** |
| ❻ 脆弱性（媒介中心性・ノード除去） | O(n·m) | 〜30万 | **数秒** |

→ **100名規模では性能は制約にならない。** 純Python実装（networkx）でも十分であり、高速ライブラリは必須ではない。
　 スナップショット生成後は、切り口を変えた再分析が**体感即時**になる。

> ⚠️ 上表は計算量からの見積もりであり実測値ではない。v0.1 で合成データによるベンチマークを行い、実測に差し替える（§12）。

#### 100名を超える場合 — 動くが、時間とコストがかかる

**動作をブロックはしない。ただし、何が重くなるかを事前に明示する。**

| 規模 | 分析 | 収集 | その他のコスト | 扱い |
|---|---|---|---|---|
| **〜100名** | 数秒 | 数分（エクスポート） | — | ✅ **公称対応範囲。検証対象** |
| 100〜300名 | 数十秒 | 10分前後 | 合意形成の手間が増える | ⚠️ 動作見込み。**検証範囲外** |
| 300〜1,000名 | 数分 | 30分〜数時間 | 情シス調整・ストレージが効いてくる | ⚠️ 時間がかかる。高速ライブラリ推奨 |
| 1,000〜3,000名 | 10〜30分 | 数時間〜 | APIレート制限が深刻化 | ⚠️ **非推奨。** 事業部単位の分割を推奨 |
| 3,000名超 | 時間オーダー | 日オーダーになりうる | 運用負荷が本格化 | ❌ **想定外。** 別の手段を検討すべき |

**ここでいう「コスト」は計算時間だけではない。** 規模が増えると以下が同時に重くなる。

| コスト | 内容 |
|---|---|
| **収集時間** | APIのレート制限により、大規模では初回収集が日オーダーになりうる（§10.2） |
| **情シスの工数** | 組織が大きいほど権限付与・セキュリティレビューの調整が重い |
| **合意形成のコスト** | 社員への開示・同意取得（PR-3）は人数に比例して重くなる。**技術的な問題より先にここで止まる** |
| **ストレージ** | 3,000名超で数GB規模。本文を保存しない設計でもバックアップ運用が必要になる |
| **分析の妥当性** | ❶❷は比較可能な集団内でしか意味を持たない（FR-5.2）。大規模では全社一括のランキングがそもそも解釈できない |

#### NFR-4 段階的縮退 — 規模超過を「気づいたら遅い」にしない

- **FR-5.5 規模チェック**（簡素化）
  - `relana init` および `snapshot create` の時点で**対象人数を検出し、100名を超えていれば警告を表示**する
  - 警告内容: 想定所要時間、検証範囲外である旨、分割分析という選択肢
  - **停止はしない**。`--yes` なしでも続行できるが、所要時間の見込みを提示して確認を求める
  - `relana doctor` とレポート表紙にも「対象人数 N名（公称対応範囲: 100名）」を表示する
- **README に対応規模を明記する**（NFR-10）。「◯名まで検証済み」という形で、検証した範囲と未検証の範囲を区別して書く

### 10.2 収集側の規模感 — ボトルネックは人数ではない

**収集の所要時間は従業員数ではなく「イベント量 × APIのレート制限」で決まる。** 計算量の話とは別物。

| 従業員数 | 四半期あたり推定イベント数 | ディスク | エクスポート取込（方式B） | API接続（方式A） |
|---|---|---|---|---|
| **100人（ターゲット）** | 約35〜50万 | **数十MB** | **数分** | 数十分〜数時間（下記の制限次第） |
| 300人 | 約100〜150万 | 100MB級 | 10分前後 | 時間オーダー |
| 1,000人 | 約350〜500万 | 数百MB | 30分前後 | 数時間〜 |
| 3,000人 | 約1,000〜1,500万 | 1GB級 | 1〜2時間 | 日オーダーになりうる |

- 前提: 1人1営業日あたり50〜80イベント（Slack 20〜40・メール 30〜50・会議 3〜5）、四半期＝約62営業日
- **ディスク量が小さいのは本文を保存しないため**（FR-1.5）。本文を保存する設計なら1〜2桁増える

#### API接続（方式A）が遅くなりうる理由 ⚠️ 要検証

- チャットSaaSの履歴取得APIは**レート制限が厳しい場合がある**。制限が「毎分1リクエスト・1回15件」といった水準だと、
  10万件の取得に数日かかる計算になる（一方、緩い枠なら同じ量が十数分で終わる）
- **各SaaSの現行のレート制限は実装前に必ず実測で確認すること**（仕様変更が起きやすい領域）
- → **これが「エクスポート取込（方式B）を先に作る」判断の最大の根拠**（§12 v0.1、Q16）。
  管理コンソールのエクスポートはレート制限を受けないため、**規模によらず最短経路になる**
- **100名規模ならエクスポート取込で数分**なので、方式Bだけでも実用上まったく困らない

#### 収集側の設計要件（再掲・補強）

- 時間がかかること自体は許容する。**中断・再開（FR-1.7）と進捗表示があれば運用は回る**
- 初回収集は一度きり。以降は差分収集（FR-1.8）なので日次で数分に収まる
- `collect --dry-run`（FR-1.6）が**実行前に所要時間を提示**するため、担当者が驚かない

### 10.3 下限と個人特定 ★100名規模ではこちらが本質的な制約

**100名規模で問題になるのは性能ではなく、①分析の成立性 と ②個人特定を前提とした設計 である。**
ターゲットを100名に定めた以上、**この2つが本OSSの主要な設計課題になる。**

#### ① 分析の成立性

| 指標 | 100名での成立性 |
|---|---|
| ❺ サイロ | ✅ 成立（部門3〜4個・各20〜30名あれば I/E 比は十分に意味を持つ） |
| ❻ 脆弱性 | ✅ 成立。**小規模組織ほどブリッジ役が1人に集中しやすく、むしろ検出価値が高い** |
| ❸❹ 効率性・イノベーション | ⚠️ 成立するがチーム数が5〜10個程度で、4象限プロットの点が少ない |
| ❶ 発想力・❷ 影響力 | ⚠️ 成立するが、部門内パーセンタイルの母数が20〜30名のため**順位が粗く、変動しやすい** |

- **推奨下限は50名、快適に意味を持つのは100名前後**（目安。要検証）
- **30名未満ではネットワーク構造が単純すぎて構造的特徴が分散しない** → 警告を出す（FR-5.5）
- ❶❷ については、**順位の粗さを結果に明記する**こと（`caveats` に母数を書く）。
  「部門内2位」が実は20名中2位であることを隠さない

#### ② 個人を特定する前提での設計 ★

**方針: 匿名化は行わない**（§9 冒頭）。誰がどのような状態かを把握することが人事の職務であり、
100名規模では匿名化しても誰が誰かは分かるため、**匿名化は実効性を持たないまま出力だけを劣化させる**。

- k匿名（k=5）は100名規模・部門20名程度では頻繁に発動し、**出力の多くが空になる**
- ❻脆弱性（アルビンド検出）も❷影響力（真のインフルエンサー特定）も、**実名でなければ打ち手に繋がらない**
- → **L2（個人スコア・実名）を既定**とし、守りは **PR-2 アクセス制御** と **PR-3 透明性** に移す

**100名規模だからこそ成立しやすい条件もある。**

| 条件 | 100名規模での状況 |
|---|---|
| 全社への開示 | 全社集会やSlackで**一度に全員に説明できる**。大企業より圧倒的に容易 |
| 同意の取得 | 100名分の合意書は現実的な工数で回る |
| 本人への還元 | 100名分の個人レポートは数分で生成でき、1on1に組み込める |
| 経営層との距離 | 結果を見る人と見られる人の距離が近く、**説明責任を果たしやすい** |

> 開示を行うかどうかは運用判断であり、本OSSは要件としない（FR-1.18.5）。
> **匿名化せず開示も必須としない以上、防御は PR-2 のアクセス制御に一本化される。**
> 「誰が結果を見られるか」の設計が、本OSSにおける唯一の実効的な統制となる。

#### 重みとノイズ除去が性能にも効く

- FR-4.5 のノイズ除去（全社通知チャネルの除外、最小相互作用回数の閾値）は、**❶ の `d_i²` を直撃する**
- 100名規模では性能影響は軽微だが、**全社アナウンスチャネルを含めると全員が全員と繋がった密なグラフになり、
  構造的特徴そのものが消えてしまう**（サイロも脆弱性も検出できなくなる）
- → 小規模組織ではノイズ除去は**性能要件ではなく、分析が成立するための必須要件**である
